# レビュープロセス設計(採用版)

**この文書が正本である。**#256 でゼロベースに設計し、POが採用を決定したもの。

**まだ施行されていない。**本書は「何を、いつ、何を根拠に、どう判定し、どうなったら通すか」を定める設計であり、
**実装(workflow・設定・スクリプト)は含まない。**現行との突き合わせと移行は後続Issueで扱う。

検討の経緯は `docs/research/review-process/` にある(3草案・評価・統合案。いずれも**検討記録**であって正本ではない)。

## 1. 何のためのプロセスか

このリポジトリは**人間がdiffを読まない**前提で運用し、変更はほぼすべてAIエージェントが書く。
人間はPO1名である。品質担保の第一原理は**「壊れたらCIが赤くなる」**。

したがってレビューが答えるべき問いは「このコードは読みやすいか」ではなく、
**「人間がdiffを読まないまま、`main` に入れてよいか」**である。

> **機械が止められるものは、レビューの仕事ではない。**
> **レビューの持ち分は、緑のまま間違っている変更だけである。**
>
> **止めたいものは、必ず required check の赤として表現する。**
> 表現できないものはレビュー判断の対象として残し、**その判断が行われたこと自体を、また赤で守る。**

`main` はRulesetで保護されており、**マージを機械的に止められるのは required status check だけ**である。

## 2. 単位

**1 Issue = 1判断 = 1ブランチ = 1 PR。**

PRを使う理由は1つだけで、**保護された `main` に入れる経路が他に無いから**である。
PRは「1つの判断を包む容器」であって、レビューの単位そのものではない。
**1つのPRに2つの判断が入ると、残余(§10)の計算が破綻する** ——
どちらの判断についての残余なのかが言えなくなる。

**生成物のみの変更**(生成型の再生成、整形、ロックファイル更新)は同じPRに混ぜず、
別に流して機械ゲートのみで通す。

**fork由来のPRは通常経路に乗せない。**理由は2つあり、どちらも単独で十分である。

1. fork PRでは `GITHUB_TOKEN` 以外のsecretがrunnerに渡らず、証拠収集に必要な権限を持てない
2. **fork PRでは SHA→PR の逆引きが両経路とも空になる**
   (`commits/{sha}/pulls` と `check_run.pull_requests` の実測。`docs/research/review-process/integration.md` §4.3)

### 束ねPRも本設計の対象単位である

**複数のIssueを1本のPRにまとめる「束ねPR」は、本設計の対象単位に含む。**

**上の「1 PR = 1判断」と衝突しない。**束ねの共通条件が
**「着手時点で、束ねる各Issueの残り作業に判断が残っていないこと」**を要求しているため、
**束ねPRは判断0個のPRである。**「1つのPRに2つの判断」には当たらず、
**残余(§10)の計算が破綻するという根拠も、判断0なら成り立たない。**

**条件・上限の正本は `docs/task-management.md`「Issueを束ねて1本のPRにする」。ここに書き写さない。**

束ねたときの各段階の扱い:

| 段階 | 束ねたときの扱い |
| --- | --- |
| **S0 契約** | **束ね単位で1つ書く。**触る面は**和集合**、不可逆等級は**最大値**、予測される残余は**件ごとに分ける** |
| **S3 契約適合** | **その和集合に対して判定する** |
| **S10 打ち切り** | 「変更を割る」に**「束ねを解く」を含む** |

## 3. 段階

| 段階 | 発火契機 | 担当 | 出力の面 | 次へ進む条件 |
| --- | --- | --- | --- | --- |
| **S0 契約** | Issue を In Progress へ | 実装エージェント | Issue/Sub-issue 本文の固定見出し | 契約5項目(§4)が埋まっている。不可逆等級 R2 以上なら**着手前に**PO確認 |
| **S1 ローカル** | 変更を書き終えた時点 | 実装エージェント | ローカルのみ | `yarn lint && yarn typecheck && yarn test` が緑 |
| **S1.5 ローカルレビュー** | S1が緑 | 実装エージェント | ローカル + PR本文への記載 | 指摘内容と対処がPR本文に書かれている(§5)。**Draft PRを作成する** |

| **S3 契約適合** | S2が緑 | 自前ジョブ(関門ジョブの内側) | check run(**required**) | 変更パス集合が契約の「触る面」に収まる(§7) |

| **S5 収集と判定** | S2〜S4の後、**常に実行** | 関門ジョブ | check run(**required**) | **必須2本の陽性証拠が揃う**(§8.3) |
| **S6 指摘の処置** | S5が指摘を返した | 実装エージェント | 追加コミット + PR本文の指摘台帳 | **未処置0件。**処置は4値(§9) |
| **S7 残余の提示** | S5合格かつ残余が空でない | 自前が生成、POが読む | Issueコメント | **POの応答1回。**空なら不介入で進む(§10) |

| **S9 マージ** | required checks が全緑 | 実装エージェント | `main` | Ruleset を満たす。マージ後 worktree を畳む |
| **S10 打ち切り** | **2巡しても指摘が閉じない** | 実装エージェント → PO | Issue | **レビューを足さない。変更を割って別Issueにする。**3巡目に入らない |
| **S11 事後** | マージ後に不具合が出た | 人 + エージェント | Issue | 「どのゲートが取り逃がしたか」を特定し、**ゲート強化のPRを起票する** |

**S10 は3回ルール(機械的に解決しない)ともPO確認(判断が割れている)とも別の対処である。混ぜない。**

### S11 は、全PRの振り返りのうちゲートに関わる部分を強めたものである

**全PRを対象とするマージ後の振り返りは、本設計の対象外である。ただし廃止しない。**

**S11 はその振り返りの一部** —— **「マージ後に不具合が出たとき、どのゲートが取り逃がしたか」**
——**を取り出して強めたものであり、振り返り全体を置き換えるものではない。**

**振り返りの正本は現行プロセス側にある。移管先は施行時に決める(§14)。ここに書き写さない。**
片方だけ古くなるためである。

## 4. 契約(S0)

**着手前に、実装エージェントが次の5項目を書く。**

1. **触る面** —— ディレクトリ、テーブル、RLSポリシー、`docs/` のどのファイル
2. **変えない不変条件** —— 権限マトリクス、既定値、削除の意味論、`common/` の2経路同期
3. **変える不変条件** —— 空でなければ自動的に不可逆等級が上がる
4. **不可逆等級** —— R0 コードだけ / R1 設定・CI / R2 永続データ・マイグレーション・公開API・`docs/` の意図 /
   R3 上記のうち他者に観測済みのもの
5. **予測される残余** —— 機械が検査しないが、この変更が正しいために真である必要があること

**不可逆等級はレビューの深さを決める。**深さを行数ではなく「元に戻せなさ」に比例させる ——
**300行のUI変更より、1行の `default false` → `default true` のほうが深い。**

> **等級による分岐は、必ずゲートジョブの内側で行う。**
> job-level の `if:` や path フィルタでスキップしてはいけない。
> **skipされたjobは `"Success"` を報告し、required check であってもマージを妨げない。**
> ここを外すと、深さの分岐がそのまま「静かに通る穴」になる。

## 5. ローカルレビュー(S1.5)

**位置づけ: 品質担保の絶対条件ではなく、足切り／事前チェックである。**

- **ここで拾えなかったものは、PR内のレビューで拾う**
- **ここを通ったことを、合格の根拠にしない**

**系統は Claude で行う。**

**独立性には2つの軸があり、S1.5 は片方だけを緩める。混ぜない。**

| 軸 | S1.5 での扱い |
| --- | --- |
| **系統の独立性**(Claude か Codex か) | **緩める。**必須ゲートの1本目(§8.3 `claude-code-action`)と同系統でよい |
| **セッションの独立性**(新規か、実装セッションの継続か) | **緩めない。要求する** |

**系統を緩めてよい理由は、S1.5 に独立した検知を期待していないからである。**
§8.1 の「揃えすぎると4系統が相関し、複数持つ意味が減る」は**必須ゲートを構成する系統の話**であって、
S1.5 には掛からない。**S1.5 は合格の根拠にしない足切りだからである。**

> **S1.5 の価値は、他系統の枠を使う前にノイズを落とすことにある。**

**セッションの独立性は緩めない** ——
**実装に使ったセッションを継続しない。**
**実装時に置いた前提をそのまま引き継ぐと、前提そのものの誤りを見落とすためである。**

**この要求は系統を揃えても消えない。**根拠が系統ではなくセッションの話だからである。

**機械が確認できる形にする** —— PR作成時に、**ローカルレビューの指摘内容とその対処をPR本文に記載する。**
**記載の有無はゲートで確認する。内容の妥当性はゲートで判定しない**(できないため)。

## 6. 機械が止めるもの(S2)

**レビューに何を残すかは、ここで決まる。**入ってはいけない欠陥を列挙し、
機械が止められるものはCI/型/テスト/DB権限の側に置く。ベンダー公式も
**「決定論的チェックはCIに残せ」**と明記している。

| 欠陥 | 機械が止められるか | 置き場所 |
| --- | --- | --- |
| `as` / `any` | 止められる | ESLint |
| インラインの `@ts-ignore` / `eslint-disable` | 止められる(要追加) | 抑制コメントの出現自体をCIで検出。設定ファイル側の例外だけ許す |
| 判断ロジックを `common/` 以外に置く・複製する | **部分的** | 層境界lint + **残余はレビュー** |
| Web UI と MCP の2経路が片方だけ古くなる | 止められる(要追加) | 同一入力集合を両経路に流し、結論の一致を assert する等価性テスト |
| 型の二重定義 | **部分的** | 生成型の差分検出 + **残余はレビュー** |
| 権限マトリクスの行が片方の層にしか無い | 止められる(要追加) | マトリクスを機械可読な単一データにし、RLSテストとアプリ層テストの両方をそこから駆動 |
| `test/db/` で service_role を使う | 止められる | 参照をCIで検出 |
| 既定値(参加登録の非公開)の反転 | 止められる | 既定値を固定するテスト |
| イベントの物理削除 | 止められる | DB側でDELETE権限を外し、否定側テストで固定 |
| 静かに失敗する変更に否定側テストが無い | **部分的**(要追加) | 変更行に対する故障注入。条件を反転しても緑なら赤にする。**カバレッジ率では代替できない** |
| 成果物どうしの矛盾 / 確認せず決めた判断 | **止められない** | **レビュー判断とPO確認** |
| ガバナンス文書の正本が複数箇所に増えた | **止められない** | **レビュー判断** |
| 自動化設定の権限拡大・skipの穴・永久pending・fork PRのsecret | **部分的** | 静的検査 + **残余はレビュー** |

**レビューの持ち分は、上表の「止められない」と「部分的」の残余だけである。**
移せるものをレビューに残すのは、レビューの枠を機械が言えることに食わせる分だけ損になる。

## 7. 契約適合(S3)

**変更パス集合が、S0の契約の「触る面」に収まっているか。**

- **はみ出したら不合格。**スコープクリープはここでだけ止まる
- **R2の面に触れているのに契約の不可逆等級がR1以下なら不合格**

判定は関門ジョブの内側で行う。ゲートはこの判定のために変更ファイル一覧をどのみち読む。

## 8. レビューの実行と判定(S4・S5)

### 8.1 観点と読める範囲 —— どちらも下限を揃え、上限は開ける

#### 観点

**`AGENTS.md` の `## Code Review Rules`(P0/P1の定義)を4系統すべてに配る。**
**「これ以外を見るな」とは書かない。**各系統が自分の得意で追加の指摘を出してよい。

- **下限を揃える理由:** 揃っていないと系統の入れ替えが等価にならず、
  §8.3 の「いずれか1本」「2本」が担保にならない
- **上限を開ける理由:** 揃えすぎると4系統が相関し、複数持つ意味が減る。
  加えて、共通のルールが誤っていたときに4系統が同じ誤りをする

**配布の実現方法は系統ごとに異なる。**本設計は「配る」ことだけを定める。

#### 読める範囲

**観点を配っても、差分しか読めない系統はその観点を満たせない。**
§6 がレビューに割り当てた欠陥のうち、次の4つは**差分の外を読まないと検出できない。**

- 判断ロジックを `common/` 以外に置く・複製する(複製の検出には他ファイルを見る必要がある)
- 型の二重定義
- 成果物どうしの矛盾
- ガバナンス文書の正本が複数箇所に増えた

> **読める範囲の下限は、§6 でレビューに割り当てた欠陥を検出できる水準とする。**
> **上限は開ける。**

**具体値は本設計では決めない。**各系統の設定の所在に依存するためである(§14)。

### 8.2 Draft期とReady後の配分

**PRはDraftで作成する。Draft中は反復に使える系統を回し、残りはReady化まで当てない。**

**配分の原則:** **1PRあたりの起動回数が多い系統をDraft期に、少ない系統をReady後に当てる。**
回数の少ない系統ほど、当てるタイミングが結果を左右する ——
**粗い状態に1回だけ当てるより、整った状態に当てるほうが得られるものが多い。**

**Ready化の条件:** S2・S3が緑で、Draft期の系統からの指摘に処置(§9)が付いていること。

**具体の割り当ては本設計では固定しない。**各系統が1PRあたり何回動くかの現在値に依存するためである。

### 8.3 必須ゲート —— 2本。ただし2本目は固定しない

**マージには、対象SHAに対する陽性証拠が2本必要である。**

| | 内容 |
| --- | --- |
| **1本目** | `claude-code-action` |
| **2本目** | **残り3系統のいずれか1本。**どれが埋めてもよい |

- **どの系統が2本目を埋めたかを、ゲートが記録する**(後から「何が見たか」を辿れるようにする)
- **2本揃わなければ赤。**マージできない。**pending にはしない**

#### 自分自身を変更するPRの例外

> **あるレビュアーの設定・実装そのものを変更するPRでは、その系統の実行結果を当てにしない。**
> **自分を変更した状態の自分が、正しく動く保証が無いためである。**

**`claude-review` に関わるファイルを変更するPRでは、`claude-code-action` を必須から外し、
代わりに残り3系統から2本を要求する。**

- **判定はゲートの内側で行う。**ゲートは契約適合(§7)のために変更ファイル一覧をどのみち読むので、分岐1本で足りる
- **required check を追加しない。PO承認も bypass も経路にしない**
- **`--admin` による bypass を定例の経路にしない。**個別の required check だけを選んで迂回する機構は存在せず、
  全体を飛ばすことになるため、**記録が「何が緑で何が赤だったか」を失う**

**他の3系統についても同じ原則が掛かる。**どのファイルの変更がどの系統に対応するかの具体化は、
各系統の設定の所在を確認できる場で行う。**本設計は原則のみを定める。**

### 8.4 取得の作法

- **面を4つとも取る** —— `pulls/{n}/reviews` / `pulls/{n}/comments` / `issues/{n}/comments` /
  `commits/{sha}/check-runs`。**片方だけ見ると指摘を丸ごと取り落とす**
- **`per_page=100` を明示し `Link` の `rel="next"` を辿る。**既定30のまま打ち切ると静かに欠落する。
  1ページに収まると `Link` が付かないので、**`Link` の不在を異常と読まない**
- **check run は `filter=all`。**既定 `latest` では再実行前が見えない
- **スレッド解決状態は GraphQL の `PullRequestReviewThread.isResolved`。**RESTに対応フィールドが無い。
  **不在に賭けるのではなく、存在する側を使う**
- **botの同定に `login` を使わない。**`user.type == "Bot"` と既知の `user.id` の**両方一致**を要求し、
  どちらか外れたら「同定不能 = 未実行扱い」
- **reviewが増えたことを「本文が投稿された」と読まない。**`body` が空の review が作られる実例がある
- **PR番号はイベントペイロードから取る。**SHA→PR の逆引きは補助にとどめ、**自前の照合表は作らない**
- **実行回数を `run_attempt` で数えない。**あれは試行番号で初回が `1` である

### 8.5 判定の原則

> **「否定の証拠が無いこと」を成功の根拠にしない。**
> 各系統について**陽性の証拠**を定義し、取れなければ「未実行」として扱う。
> **「不明」は「未実行」と同じ扱いにする。**

**使ってはいけない信号:**

- **CodeRabbit の commit status** —— スキップ時も `Review completed` / `success` を返す
- **Copilot の review `state`** —— 成功時も quota 拒否時も `COMMENTED` で一致する
- **ベンダーの集計API / ダッシュボード** —— 値域が表示系と食い違い、合否の根拠に使えない
- **`combined status` の `state`** —— ステータス0件のコミットは `success` ではなく `pending` になり、
  「成功」と「何も出ていない」が潰れる。`total_count` を見る
- **`bypass_actors` の `null`** —— 権限が無いと `null` が返り、「いない」と「見えない」が潰れる

**想定外の値は失敗に倒す。**check run と check suite で `conclusion` の値域が違う
(check suite だけが `stale` / `startup_failure` を持つ)ので、値域を分けて扱う。

### 8.6 陽性証拠が足りず赤になったときの出口

**必須2本が揃わず赤になったとき、そこで止まったままにしない。**

| 状態 | 出口 |
| --- | --- |
| **不在の信号が待ち時間を明示している** | その時間だけ待って**1回だけ再試行**。**上限は1時間** |
| 待ち時間が明示されていない | **PO報告** |
| 明示されているが1時間を超える | **PO報告** |
| 理由が判別できない(「不明」) | **PO報告** |
| **同一PRで待ちに入るのが2回目** | **PO報告**(待ちを繰り返さない) |

**ベンダー名で分岐しない。**「この系統なら待てば戻る」という決め打ちをしない。
**判定はあくまで「その信号が待ち時間を持っているか」で行う。**

**S10(2巡しても閉じない)とは別の経路である。混ぜない。**
S10 は**指摘が閉じない**場合、本項は**指摘が来ない**場合。

### 8.7 POの承認(S8)は GitHub の approve に限定しない

**通過条件は「POが明示的に承認したことが機械的に確認できること」である。**

**GitHub の approve をそのまま使えない** —— **POとPR作成者が同一のGitHubアカウントであり、
GitHubは自分のPRの承認をカウントしない。**approve を条件に据えると Phase 3 で実装できない。

**具体的な形式(Issueコメント / ラベル / PR本文のマーカー等)は本設計では決めない**(§14)。
**要件は1つだけ** —— **ゲートが機械的に読めること。**人がUI上で見て納得した、では条件を満たさない。

### 8.8 起動回数を抑える機構は新設しない

**「1PRで複数回走らせない」ための制御を、我々の側で新たに作らない。**
系統側の設定で足りる範囲に留める。**手動での再発火は規律で持つ。**

## 9. 指摘の処置(S6)

**指摘IDと1対1の型付き処置を要求する。**自由記述のまとめコメントにしない ——
**「読んだ」を機械が数えられる形にしないと、処置の欠落が静かに通る。**

**処置は4値: 適用 / 反論 / 別Issueへ送る / 見送り。**反論・別Issueへ送る・見送りは理由を書く。

**「別Issueへ送る」が要る理由は、§7 の契約適合と衝突するからである。**
§7 は「変更パス集合が契約の触る面からはみ出したら不合格」とする。
したがって**契約の外の面に対する妥当な指摘は「適用」できない** —— 適用すればS3で落ちる。
「見送り」は*やらない*の意味なので、**追跡が残らない。**
**S10 は指摘が閉じない場合の経路なので、ここには効かない。**
4つ目が無いと、**「妥当だが今回のPRの範囲外」という指摘に合法な出口が無くなる。**

**型の数は、巡回数の発散とは別の軸である。**指摘IDと1対1・機械が数えられるという要件は壊れない。

**「適用」には、符号化の記録を伴わせる** ——
**その指摘を実行可能な検査(テスト / lintルール / CIの検査 / `docs/` に書かれた決定)に
符号化したか。していないならその理由を書く。**

> **符号化されない指摘は必ず再発する。**人間がdiffを読まない以上、再発は次も同じレビューコストで検出するしかない。

これは S11(マージ後の取り逃がし → ゲート強化のPRを起票)の**事前版**である。
**事後版だけがあって事前版が無いのは非対称だった。**

**ベンダーの重大度で足切りしない。**Codex の値域だけで公式(P0/P1)・他社実測(P1/P2/P3)・
アナリティクス画面(P0/P1/P2)・集計スキーマ(`p0`/`p1`/`p2`)の**4つが食い違い、確定不能**である。
**値域が確定しないものを分岐条件にすると fail-open になる。**

**発散は畳み方で止める。観点を絞ることで止めない。**

- 処置の4値を指摘IDと1対1に対応させる
- ラウンド上限2(S10)
- **同一根拠の指摘は差分全体へ横展開し、複数箇所を列挙して1件に集約する**

**指摘を出した系統による再レビューを必須にしない。**修正が必須2本に見られていれば足りる。

## 10. 残余(S7)

**残余 = 「この変更が正しいために真である必要があるが、誰も検査していないと特定できた性質」。**

- **必須本数が揃えば、残りの系統の不在は理由を問わず残余に積まない**
- **揃わなければ残余ではなく、ゲートが赤**(§8.6の出口へ)
- **「見落としたかもしれない」は残余ではない。**それは検知の失敗として扱う。混ぜない
- この結果、**残余の流入経路は実質 S0 の契約に書いた「予測される残余」だけになる**

**残余が空でなければ、S7でPOの応答1回を待ってからマージする。空ならPO不介入で進む。**

## 11. プロセス自身の劣化を検知する

上のすべては「PRがあるときに」しか働かない。
**設定が壊れて系統が1つも走らなくなった状態は、PRが出るまで見えない。**

- **定期の合成PR(canary)** —— 無害な差分を持つPRを定期的に開き、
  ゲートが陽性証拠を取れることを確認して自動でcloseする。取れなければ人に通知する
- **月次の監査** —— 系統別の受理率・却下率・空振り率を GitHub側の面から自前集計する。
  **S5が既に全面を読んでいるので、その判定結果を残せば集計は追加コストなしで付いてくる**
- **逐語文字列の照合ロジックを pure関数として切り出し、文言が変わったら赤くなるテストを付ける。**
  ベンダーの文言は実際に変わっている(CodeRabbit のレート制限見出しが
  `## Rate Limit Exceeded` → `## Rate limit exceeded`)。
  **文言変更を「静かに通る」から「CIが落ちる」へ変換する**

## 12. いま到達できない理想

**到達できない要素を消すと、次に何を取りに行けばよいかが失われる。**

| 理想 | いまの状態 | 何が変われば到達できるか |
| --- | --- | --- |
| **レビュアーへの文脈遮断**(1周目は diff と不変条件だけを見せ、**著者の意図説明**を見せない) | `claude-code-action` 以外は入力チャネルを絞る設定が確認できた範囲に無い | **今日からできる代替:** 契約をSub-issueに置きPR本文を索引だけにする。**次の一手として最も安いのは** `claude-code-action` を2段構えにすること(1回目は**著者の意図説明を渡さず**、2回目に契約を渡して適合を問う) |
| **必答の強制と沈黙の検出** | 構造化出力を返すのは `claude-code-action` の `--json-schema` だけ | **単一で最も効くのは、ベンダーが出力本文に1行の機械可読マーカーを入れること。**CodeRabbit は既にある。Codex と Copilot は観測範囲で0件。**これが入るだけで判定の大半が逐語文字列照合から解放される** |
| **Codex を必須ゲートにできるようにする** | check run も commit status も作れない(App権限が read のみ) | **Codex GitHub Action**(自前ワークフローから回す経路。設定・課金・トリガが Automatic Reviews と別立て)。**併用時の重複と枠の別立ては公式に未記載なので、導入前に実測が要る** |
| **残余の完全な自動計算** | 意味判断が残る | **必答の構造化に完全従属する。**上が解ければ、残余は差集合として計算でき、追加コストなしで付いてくる |

> **文脈遮断の2つの軸を混ぜないこと。**
>
> - **「著者の意図説明を見せない」** —— 理想として残す。上表の行はこちらの意味である
> - **「リポジトリの他の場所を読ませない」** —— **これは §6 の割り当てと衝突するので、狭める対象にしない**
>   (§8.1「読める範囲」の下限を割り込む)
>
> **2段構えの「1回目」は前者の意味に限る。**差分の外を読ませない、という意味ではない。

## 14. 本設計に含まれないもの

**実装は含まない** —— workflow YAML、`.coderabbit.yaml` の設定値、Ruleset のJSON、
ゲートのスクリプト、required check の具体的な名前、canary の頻度と通知先、
故障注入・等価性テスト・権限マトリクス駆動テストのファイル配置とフレームワーク選定。

**本設計で意図的に確定させなかったもの:**

| 項目 | なぜここで決めないか |
| --- | --- |
| **観点の配布の実現方法**(系統ごと) | 各系統の設定の所在と現行の欠落を確認できる場で扱う |
| **レビュアーの読める範囲の具体値**(系統ごと。§8.1) | 各系統の設定の所在と現行の欠落を確認できる場で扱う |
| **ローカルレビュー(§5)の具体的な実現手段と、Codex側の実装エージェントからの実行経路** | ツールと経路の選定であり、設計の判断ではない |
| **S8 の承認の具体的な形式**(Issueコメント / ラベル / PR本文のマーカー等) | 要件は「ゲートが機械的に読めること」だけで、形式はそれを満たせば何でもよい |
| **全PRのマージ後の振り返りの移管先**(正本をどこに置くか) | 廃止しないことだけを決めた。置き場所は施行時に現行側と合わせて決める |
| **Draft期／Ready後の具体的な系統の割り当て** | 各系統が1PRあたり何回動くかの**現在値**に依存する |
| **「自分自身を変更するPR」のファイル→系統の対応**(`claude-review` 以外) | 同上 |
