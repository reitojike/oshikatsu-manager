# 権限設計とRLSの検証

権限に関わるコード(RLSポリシー、アプリ層の権限判定、参加登録・招待・削除まわり)を触る前に読むこと。

## 前提

権限制御は**二重**に行う。

| 層 | 役割 | テストでの扱い |
| --- | --- | --- |
| Supabase RLS | 最終防衛線。アプリ層をすり抜けても止める | `test/db/` で実DBに対して検証 |
| アプリ層のpure関数 | 主たる判定ロジック。UIの出し分けにも使う | `test/unit/` で検証 |

**両方に同じマトリクスを実装し、両方をテストする。**片方だけ直された状態を検出するため。

これは上表の3列すべてに等しくかかる条件で、オーナーであっても例外はない(issue #54)。
削除ガード「非オーナー参加者が1人でもいれば削除不可」(`docs/prd.md` 4.6)は、削除**後**に
参加者が増えないことまで前提にしている。両経路を塞がないとこの不変条件が事後的に破れる。
自己参加登録の経路も机上の話ではない。削除済みイベントはオーナー本人と、そのイベントに
`expenses` を持つユーザーには引き続き見えるため(下記RLSポリシー方針 ※1)、経路が実在する。

**塞ぐのは新規の参加登録・招待(INSERT)だけである。**削除済みイベントに既に存在する参加行の
ステータス変更・公開設定の変更・参加の取りやめは、これまでどおりできる。削除ガードにより、
削除できたイベントの参加者はオーナー本人しかいないため、対象は実質オーナー自身の行に限られる。

> 削除済みイベントの**復活**という操作は存在しない(削除は不可逆。詳細・根拠は
> `docs/data-model.md` 2章「削除のガード条件」)。権限マトリクスに復活の行は無い(意図して置いていない)。

**参加登録の公開設定の既定値: 非公開。**

**招待できる条件: そのイベントに参加登録しているユーザー。オーナーかどうかは問わない。**
`owner_id` は「情報の管理者」であって、イベントの主催者や招待の権限者を意味しない
(`docs/data-model.md` 2章)。したがって**オーナーであっても自分自身が参加登録していなければ

ケースを指す。招待可否はオーナーかどうかではなく、参加登録の有無だけで決まる。

## 削除時の支出データの扱い

| ケース | 予算のみ(実績未登録) | 実績が登録済み |
| --- | --- | --- |
| ユーザーが参加を取りやめた | 該当ユーザーの支出データも削除 | 支出データは残す |
| オーナーがイベントを削除した | 参加者の支出データも削除 | 支出データは残す |

考え方: 予算は実施前の見込み値なので消えても影響が小さいが、実績は家計の記録として意味を持つため保全する。イベントは論理削除なので、支出から辿ってイベント名は常に参照できる。

## RLS検証の必須要件

`test/db/` で Supabaseローカル(`supabase start`)に対して実行する。

### 1. service_roleキーを使わない

service_roleはRLSをバイパスする。これで通ったテストは、**RLSポリシーを全部削除しても緑のまま**になる。
必ず実際にサインインしたユーザーのクライアントで検証すること。

### 2. 「弾かれること」を確認する

正常系だけのテストは、権限が全開放されていても通る。否定側が本体。

```typescript
// これだけでは何も検証していない
const { data: dataA, error: errorA } = await asUserA.from("expenses").select();
expect(errorA).toBeNull();
expect(dataA).toHaveLength(3);

// これが本体
const { data: dataB, error: errorB } = await asUserB.from("expenses").select();
expect(errorB).toBeNull();
expect(dataB).toHaveLength(0);
```

**UPDATE/DELETEが「成功したかに見える」結果だけで判定しない。**
PostgreSQLのRLSでは、UPDATE/DELETEの対象行はまずコマンド自身のUSING句で絞り込まれる。
USING句を満たさない行は**エラーなく静かに除外される**(候補行が単に0件になるだけ)。
「他人の行を更新/削除しようとする」典型的な否定側テスト(例: `expenses_update_own`の
`using (user_id = auth.uid())`)はこのケースに該当し、`data`は空配列、`error`は`null`になる。

`UPDATE ... RETURNING`にはこれとは別の落とし穴もある。USING句を通過して実際に
更新された新しい行の内容がテーブルのSELECTポリシーを満たさない場合、PostgreSQL公式
ドキュメント([CREATE POLICY](https://www.postgresql.org/docs/current/sql-createpolicy.html))
の通り更新自体がエラーになる("inserted or updated rows to be returned are never
silently ignored")。単に「他人の行を更新しようとする」だけの否定側テストは、通常
USING句の時点で候補から除外されるため、このエラーには到達しない。

つまり「RETURNINGが空で、エラーも出ない」という結果だけでは、(a) `WHERE`条件に一致する行が
最初から無かったのか、(b) USING句によって正しく弾かれたのか、を区別できない。
UPDATE/DELETEを試みた後は、対象行を見られる側(本人など)の視点で、値が実際に
変化していないこと・行が存在し続けていることまで確認する。

```typescript
// 更新前に本人視点で元の値を控えておく
const { data: before, error: beforeError } = await asUserA.from("expenses").select("amount").eq("id", id).single();
expect(beforeError).toBeNull();

// これだけでは何も検証していない(WHERE不一致で0件なのか、正しく弾かれて0件なのか区別できない)
const { data, error } = await asUserB.from("expenses").update({ amount: 1 }).eq("id", id).select();
expect(error).toBeNull();
expect(data).toHaveLength(0);

// これが本体。本人(対象行を見られる側)の視点で値が実際に変化していないことを確認する
const { data: unchanged, error: unchangedError } = await asUserA.from("expenses").select("amount").eq("id", id).single();
expect(unchangedError).toBeNull();
expect(unchanged?.amount).toBe(before?.amount);
```

**INSERTの`RETURNING`にも同じ注意が必要。** 招待のように自分以外のユーザーの行を作成する
操作では、作成した本人(自分)がその行をSELECTポリシー上見られないことがある。この場合
`INSERT ... RETURNING` はINSERT自体が要件を満たしていてもRLS違反エラーを返す。
`.select()` を付けずにINSERTするか、作成された行の中身は対象ユーザー自身の視点で確認すること。

### 3. マトリクスを表のままテストに写す

上の表の×が1つでもテストされていなければ、それは検証されていない権限とみなす。
表に行を追加したら、テストにも行を追加する。

### 4. 壊して赤くなることを確認する

新しく書いた権限テストは、**対応するRLSポリシーを一時的に無効化して赤くなるか**を確認してから戻す。
確認しない限り、テストが機能しているかは永遠に分からない。

## 最小の検証セット

| 検証 | 期待 |
| --- | --- |
| 他ユーザーの支出を読む | 0件 |
| 非公開の参加登録を他ユーザーが読む | 0件 |
| オーナー以外がイベントを更新 | 失敗 |
| オーナー以外がイベントを削除 | 失敗 |
| 他ユーザーの参加ステータスを変更 | 失敗 |
| 他人の参加登録を勝手に取りやめる | 失敗 |
| 参加者がいるイベントをオーナーが削除 | 失敗 |
| 参加登録していないユーザーが他人を招待(オーナーであっても) | 失敗 |
| 削除済みイベントに自分で参加登録(オーナーであっても) | 失敗 |
| 削除済みイベントに他人を招待(参加登録済みの招待者であっても) | 失敗 |

## なぜここを最優先するか

権限の漏れは**例外を投げない**。見えてはいけないものが、エラーなしで、それらしく表示される。
ユーザーが気づくまで誰にも分からない種類の失敗なので、先に潰す。
