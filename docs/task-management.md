# Issueの粒度とモデル階層の分担

Issueを**起票・分割する**ときの目安と、1つのIssueの中で**下位モデルへ残り作業を渡す**ときの手順。
**Issueを起票・分割する前と、Issue内で下位モデルに渡す前に読む。**

モデル階層そのものの決め方(Opus / Sonnet / Haikuの分け方、3回ルール、`agent:*` ラベルと
Projectの運用)は `AGENTS.md`「タスク管理とモデルの使い分け」にある。ここには書き写さない。
プロバイダ間(Claude / Codex)の振り分けは `docs/model-routing.md`。

## Issueの粒度とPR差分サイズの目安

**起票時の書式は `.github/ISSUE_TEMPLATE/issue.md` を使う。**背景/決めること(3個以内)/
やらないこと/受け入れ条件/参照という既存慣行をテンプレート化したもの。「決めること3個・
PR差分300行」という数字の正本は下記のとおり `AGENTS.md`。「受け入れ条件」「やらないこと」は
下記「引き継ぎ計画に必ず書くこと」3・4と同じ意味で使う(対象がIssue全体か引き継ぎ計画かの
違いだけ)。「背景」「参照」に文書上の定義は無く、見出し語どおりの意味で使う。

目安の数字そのもの(判断は**3個**まで / PR差分は**300行**)と、行数から除外するものの一覧は
`AGENTS.md`「Issueの粒度と、Issue内でのモデル階層の分担」にある。ここには書き写さない。
**この節が置くのは、その2つの数字の裏付けである。**

**2つの数字は、裏付けの強さが違う。混ぜて読まない。**

### 300行 —— このリポジトリの実測で裏を取った数値

外部の実測(PR差分の中央値286行、300行未満が51%)を、mainにマージ済みのPR 26本(#9〜#63)で検証した。
**除外規則を適用する前と後の両方を出す。**片方だけ出すと、どちらの数え方の話か分からなくなる。

| 数え方 | 中央値 | 300行以下 | 超過 |
| --- | --- | --- | --- |
| 素の差分(`git show --numstat`) | 135行 | 17/26 (65%) | 9本 |
| + ロックファイルと `supabase/types.ts` を除外(パス名だけで判定できる) | 128行 | 22/26 (85%) | 4本 |
| + スキャフォールド出力と権限マトリクスを写したテスト表を除外 | 集計しない(下記) | — | **2本** |

素の差分で300行を超えるのは**9本**(#31 307 / #59 365 / #60 380 / #30 441 / #29 617
/ #18 679 / #41 698 / #32 1063 / #16 3528)。除外規則を最後まで適用すると、残るのは
**#59(365行)と #60(380行)の2本だけ**になる。落ちる7本の理由:

- `yarn.lock`: #16 3528→226、#18 679→47、#41 698→181
- `supabase/types.ts` の生成型: #30 441→150、#31 307→249
- `supabase init` の出力(`supabase/config.toml` 416行)+`supabase/types.ts` の生成型(179行、2段階):
  #29 617→22
- `yarn.lock`(60行)+権限マトリクスをテストに写した行(924行、2段階): #32 1063→79

**このリポジトリは外部の実測より小さい。**最も厳しい素の差分で見ても中央値135行なので、
300行は「現状を追認する上限」であって、これに合わせるために進め方を変える必要はない。

**3行目の中央値を出していないのは、意図的である。**26本すべてに適用するには全部の差分を読む必要があり、
しかも**同じパスでも扱いが逆になる。**`supabase/config.toml` は #29 では `supabase init` の出力(416行)だが、
PR #56 では rate limit を根拠コメント付きで手で直した6行で、除外してはいけない。
**パス名では決まらない。**この目安が機械的ゲートになり得ない理由は、まさにここにある。

**目安を超えたときは、原因を切り分けてから対処する。**判断の複数性(「3個」節の上限を超える
判断が着手前の範囲に含まれていた)が原因なら、着手前の分割の失敗として次回に反映する。
Draft後のボット指摘の連鎖
(実例: PR #140、773行)が**機械的な修正**の連鎖であれば、分割では防げない。**ボットが
新しい判断(4個目の決めごと)を露出させた場合はこの例外に当たらない。**上記「3個」節どおり
Issueを分ける(`AGENTS.md`「判断ポイントが目安を超えたときは、モデルを上げるのではなく
Issueを分ける」。モデル引き上げは対象外)。判断が割れている場合は`docs/decision-policy.md`
のPO確認に従う。300行という目安自体は変えない(理由は issue #144 参照)。

### 3個 —— 外部の実測から採ったヒューリスティック。このリポジトリでは検証していない

根拠は「1 Issueの決めごとが3個なら成功率73%、20個なら12%」という外部の実測だけである。
**このリポジトリで裏を取ることは、今はできない。**過去のIssueが判断をいくつ含んでいたかは
どこにも記録されておらず、後から数え直せないためである(行数と違い、機械的に取り出せない)。
検証されていないことを承知のうえで採る。理由は**外れたときのコストが非対称だから**で、
細かく分けすぎて失うのは起票の手間だけだが、多く入れすぎたIssueは入口から手戻りになる
(`docs/decision-policy.md`「Opus担当タスクで特に徹底する理由」)。
なお外部の実測に「4個」「5個」に対応する値はない。**3個と20個の間を推定して線を引いていない**ので、
上限は3個の側に置いてある。運用してみて分割が細かすぎると感じたら、そのときに実績で見直す。

**追記(このリポジトリ自身の実測)。**仕様確定文書を書くタイプのIssueは、1個に見えて
複数の判断を孕む。レビュー反復が突出したPRはいずれもこの型だった
(#225=17巡 / #182=16巡 / #175=16巡。平均は5.19回/PR)。上記の外部実測とは別の裏付けであり、
混ぜて読まない。

### なぜCIで強制しないのか

「これはlintではない」という規則は `AGENTS.md` にある。**理由は、行数が判断の量の
代理指標であって原因ではないから。**上の表がそのまま根拠になる。
素の行数で弾けば9本が引っかかるが、実際に判断が多かったのは2本で、
**判断がほとんど無かった #16 や #32 と、実装を伴った #59・#60 が区別できない。**
通すことが目的の中身のない分割を生むだけである。
`AGENTS.md`「絶対に守ること」に並ぶ規則は機械が判定できるものだけで、これはそこに入らない。

### 3回ルール・PO確認との関係

止まる理由は3つあり、対処が違う。**3つとも規則は `AGENTS.md` にある。
ここで並べるのは、取り違えを防ぐためである。**

| 何が起きたか | 対処 |
| --- | --- |
| 同じことを3回試して機械的に解決しない | **モデルを一段上げる**(`AGENTS.md` の3回ルール) |
| 判断が割れている / 計画に無い判断に出くわした | **判断を下せる層に上げる**(`docs/decision-policy.md`、下記「Issue内でモデル階層を分担する」) |
| 判断ポイントが目安を超えている | **上げるのではなく、Issueを分ける** |

3つ目をエスカレーションで処理しない。上位モデルに渡しても判断の数は減らないので、入口が詰まったまま
実行者だけが高価になる。逆に、**1つのIssueでPO確認やエスカレーションが何度も起きているときは、
粒度超過を疑う。**個々の判断が難しいのではなく、1回で閉じない範囲を1つのIssueに入れている可能性が高い。

**下記「Issue内でモデル階層を分担する」とは向きが違う。**粒度の目安は起票時に判断の数を絞る話、
分担は絞った後の残り作業を渡す話である。判断が3個までに収まっていれば判断フェーズは短く終わり、
残りは機械的な反復になりやすい。**粒度を守るほど分担が効く。**

## Issueを束ねて1本のPRにする

複数のIssueを1本のPRにまとめてよい条件と上限。**PR運用(Closes/Refs書式・close漏れ確認・
振り返りの記録先)は `pr-review-flow` skill「束ねPR」の節にある。ここには書き写さない。**

**束ねる入口は2つある。動機が違えば妥当な条件も違うため、入口ごとに追加条件を分ける
(issue #228)。**

| 入口 | 動機 | 実例(いずれもマージ済み) |
| --- | --- | --- |
| 独立型 | 1件ずつPRを立てるのが割に合わない | #173、#207、#217、#225 |
| 凝集型 | 同じファイルを複数件が触り、分けると同じファイルを件数分開くことになる | まだ無い(動機になったクラスタA(#128+#229+#231)は、issue #228の時点では共通条件「判断が残っていない」が未達でブロック中。#229/#128の判断確定後に着手可) |

**軽微さは判断ゼロを含意しない。**#217は軽微なdocs束ね(独立型)だったが、Draftで
P0/P1を2件検出している。独立型の判定語からは「軽微」を外し、下記の共通条件と
「触るファイルが重ならないこと」だけで判定する。

**共通条件(すべて満たすこと)**:

- **着手時点で、束ねる各Issue(またはPRで扱う範囲)の残り作業に判断が残っていないこと。**
  判断の定義は`docs/decision-policy.md`が正本(ここには書き写さない)。**「そのIssueがPO確認を
  経たか」は判定に使わない。**着手前にPO確認で判断を確定させたIssueは、むしろ通常の経路として
  束ね対象になりうる。**判断が残っている場合は、判断フェーズだけを先に単独で進めてPO確認を経て
  確定させ、実行可能な状態(ファイルを修正してPRを出せる段階)になってから束ねる。**束ねる
  タイミングを判断の後ろにずらす解き方であり、「Issue内でモデル階層を分担する」(下記)と
  同じ構造にあたる
- **束ねる本数は3件まで**(実例(PR)は4本(#173/#207/#217/#225)に増えたが、いずれも束ねた
  件数は3件以下。見直し条件「1本のPRに4件以上のIssueを束ねた実測が積めたら見直す」を
  満たさないため据え置く。issue #228)。`Closes`で閉じる件数と、下記「部分解決」の`Refs`で
  載せる件数を合算して数える
- **件ごとの受け入れ条件が独立に判定できること。**1件のテスト失敗が他の件まで巻き添えに
  しないよう、変更を件ごとに切り分けられる形にする

**分類(`governance-docs`/`automation-config`/`code`)による制限は設けない**(issue #228。
旧規則の`governance-docs`限定は実例PR #217(`.mjs`のロジック変更を含む)を排除しており、
既存の束ね実例を通せなかった。リスクは分類ではなく上記の共通条件で受ける)。
**ただし分類をまたぐ束ねPRでは、`pr-review-flow` skillが定める`governance-docs`単独PR限定の
反復打ち切り条件が使えない。**指摘が尽きるまで反復する前提で計画すること。

**入口ごとの追加条件**:

- **独立型**: 触るファイルが重ならないこと
- **凝集型**: 束ねる理由(同一ファイルを触ること)と、PR内での適用順序をPR本文に明記すること

**部分解決。**Issueの一部の範囲だけをこのPRで解決し`Closes`で閉じない場合は`Refs`を使う
(書式は`pr-review-flow` skill「束ねPR」が正本。PR #207の実例)。残る範囲は対象Issueに追記する。
上限の数え方は上記のとおり`Closes`と合算する。

**束ねを解く。**`pr-review-flow` skill「Ready後の運用」が定めるReady化以降の反復上限
(`ready_for_review`以降「push→明示依頼→修正」を3回行ってもP0/P1指摘が枯れなければ
Blocked化してPOへエスカレーションする。旧「5巡警報」を置き換えた基準。#244)に達したとき、
**束ねPRでは「Issueを分割する」ではなく「束ねを解く」を、POへ諮る選択肢として提示する。**
最も遅い1件に他の件が引きずられていないかを確認する。解ける前提になるのは次の両方を
満たす場合。

- その1件を外した残りが、単独で受け入れ条件を満たしCIが緑になる
- 外した件は切り出した単独PRの本文で`Closes`/`Refs`を付け直し、元のIssueには残る範囲だけを
  追記して、単独PRとして仕切り直す

**解くかどうかを自分で決めない。**参照先の反復上限は到達した時点でBlocked化とPO確認を
求めるものなので、束ねを解くかどうかもその確認の中で決まる。**切り離しのpushにCopilotの
手動再レビューが要る場合は、再リクエスト枠(1PRにつき1回。`pr-review-flow` skill
「Ready後の運用」が正本)の残りにかかわらず、都度POの承認を取ってから実行する。**
束ねを解く判断と同じ場で諮るときも、承認は別項目として明示的に取る
(束ねを解く承認に黙って含めない)。

**このトリガーが働くのはReady化以降だけである。**Draft中に束ねの膨張へ気づく巡数ベースの
合図は無く、Draft中は`pr-review-flow` skillの内容ベースの打ち切り条件だけが効く。

**PR差分の300行目安。**`AGENTS.md`の300行目安(1つの**Issue**に複数の判断が入っていないかを
疑う指標)は、**単独IssueのPRにはそのまま適用する**(`AGENTS.md`側は変更しない)。
**束ねPRでは、この節限定の例外として**、PR≠Issueになるため**束ねた件数×300行を
目安とする**(3件束ねるPRなら900行までを目安とする)。判断の量は件数に比例してスケールするので
原文の趣旨に忠実である。

根拠(#173の実測)は `docs/pr-review-flow-details.md` を参照。既存の束ねPR実例(#173/#207/#217/#225)
とクラスタAへの新条件の当てはめは issue #228 のコメントに記録済み。

## Issue内でモデル階層を分担する

**判断のフェーズと機械的な反復のフェーズを分離し、後者を下位モデルに渡す**という規則そのものは
`AGENTS.md` にある。**この節が置くのは、渡してよいかの基準線と、渡すときの手順である。**

判断の質を落とさずにコストが下がることは実測されている(実例: issue #43。方針決定の後に続いた
レビュー7巡と「壊して確認」19+13件が、Opusのまま実施された)。

**渡してよいかの判定は1問**(規則は `AGENTS.md`「渡してよいかは1問で切る」)。
その1問に当てる**基準線は階層ごとに違う。**

- **Opus→Sonnet**: 根拠が `docs/` と引き継ぎ計画に**文章として書かれている**こと。
  書かれていない設計意図を推測させることになるなら、まだ渡さない
- **Sonnet→Haiku**: 根拠が**機械の出力**(lint/tsc/testの赤緑、`yarn gen:types` のdiff、
  CIの結果)だけで決まること。文章を読んで解釈する余地が残っているなら渡さない
  (`AGENTS.md`「Haikuに任せてよいのは…」がそのまま下限)

**渡さない下限。**引き継ぎには計画を書くコストがかかる。**次の両方**を満たすときだけ分担する。

- 残りに**機械的な反復が2ラウンド以上**見込まれる(レビューボットの往復、壊して確認の反復、
  CI待ちの繰り返し)
- **引き継ぎ計画が、自分で最後までやるより短く書ける。**計画に書くことが実質diffの写経に
  なるなら、書かずに自分でやったほうが安い

**引き継ぎ計画に必ず書くこと**(書く場所は `AGENTS.md` のとおりSub-issueの本文。
セッションの中だけの合意は次のセッションに残らない)。「あとはよろしく」で渡さない。
下位モデルが意味判断を再導出せずに済む粒度で書く。**穴埋めテンプレートは
`docs/handoff-template.md`。**項目の定義はここが正本で、テンプレート側には転記しない。

1. **決まったこと**と、その根拠になった成果物の該当箇所(ファイルと節)
2. **変更対象の列挙**(ファイル・パターン・文言・テストケース)。「等」で終わらせない
3. **受け入れ条件。**どのコマンドが緑になれば完了か
4. **やらないこと。**判断済みで意図的に見送ったものを含む。
   これが無いと下位モデルが良かれと思って判断を足す
5. **予見できる分岐と、そのときの既定の選択**

**計画に無い判断の差し戻し先が、一段上ではなく「その計画を書いた層」なのはなぜか**
(規則そのものは `AGENTS.md`)。3回ルールは「同じことを試して失敗する」ためのもので、
判断の欠落は試行回数では埋まらないからである。だから3回を待たずに即座に上げる。
判断が成果物間の矛盾に由来するなら `docs/decision-policy.md` に従う。

**「計画を書いた層」は最初の宛先であって、終端ではない。**受け取った層にとっても自分では
決められない種類の判断(成果物間の矛盾など)なら、その層が通常どおりさらに上げる。
Opus→Sonnet→Haikuと多段で渡している場合、Haikuの差し戻し先はSonnetだが、
Sonnetがそこで選んでよいことにはならない。**宛先の決め方が変わるだけで、
どの層が何を決めてよいかの基準は変わらない。**

**渡し方は2通り。どちらでもSub-issueは立てる。**

- **サブエージェント**(既定): 起動する側が相手のモデルを指定してサブエージェントを立て、
  Sub-issueの番号を渡す。人間がモデルを切り替える手間がなく、計画に無い判断に
  当たったときの戻り先がそのまま呼び出し元になる
- **セッションごと切り替える**: 残りが長時間に及び、呼び出し元を待機させる意味がない場合。
  人間が次のセッションを担当モデルで開く

**サブエージェントは毎回コールドスタートする。**ここまでの会話は引き継がれないので、
**Sub-issueの本文だけで作業が完結するか**が、そのまま渡せるかどうかの判定になる。
上記「引き継ぎ計画に必ず書くこと」は儀式ではなく、この前提条件そのものである。

**Codexに渡すときも上の5項目は必須で、そこに4項目を足す**
(実行環境と権限、現在の作業状態、必読資料と読む順序、差し戻し契約)。
各項目の中身は `docs/model-routing.md`「プロバイダをまたぐ引き継ぎ計画」、
足す理由は `docs/model-routing-details.md`「引き継ぎに4項目を足す理由」。
**階層(`agent:sol`/`terra`/`luna`)を指定する引き継ぎは `mcp__codex__codex`(MCP)を既定経路とする。**
プロファイルから解決した `model` と対象worktreeの絶対 `cwd` を明示して渡す。CLIはMCP経路自体が
失敗したときの限定的なフォールバックに留める(`docs/codex-profiles.md`「階層をCodexへ渡す
(既定はMCP)」、issue #166)。

**方向は下向きだけではない。**規則は
`AGENTS.md`「`agent:opus` のIssueに着手するときは、判断フェーズをOpusのサブエージェントに投げる」。
**上向きに渡すときは制約が2つある。**

- **判断の記録を、呼び出し元に要約させない。**Opusのサブエージェントは、決めたことを
  Issueコメント・`docs/`・Sub-issueの本文に**自分で書いてから**返す。下位モデルが受け取った
  文章を要約して記録すると、判断の根拠が静かに薄まる
  (`docs/decision-policy.md`「セッションの中だけの合意はセッションの外に残らない」と同じ理由)
- **PO確認をサブエージェントの中で完結させない理由**(規則は `AGENTS.md`)。ここを飛ばすと、
  機械が止められない唯一の種類の誤りを、サブエージェント境界の内側で握りつぶすことになる

### 追跡はSub-issueで行う

- 親Issueのラベルと `Model` を書き換えないのは `AGENTS.md` の規則。以下はSub-issue側に足す手順
- Sub-issue: 引き継ぎ先の `agent:*` ラベルとProjectの `Model`(通常のIssue運用と同様、
  両方を対応させる)、親の `phase:*` ラベルをそのままコピー(`phase:2-backlog` のような
  番号だけでは表せないラベルもあるため)、Projectに登録して `Status` を Todo → In Progress。
  受け入れ条件を満たしたら、担当したモデルが `Status` を `Done` にしてIssueをcloseする。
  「PRは分けない」ため通常の `Closes #N` によるSub-issueの自動closeは効かない(親Issueの
  `Closes #N` は親のみを指す)。close忘れは機械的に検出できないため、受け入れ条件達成の
  確認と同じタイミングで行うこと
- **PRを分けない理由**(規則は `AGENTS.md`): Sub-issueは作業の追跡単位であってPRの単位ではない。
  分けると、実装途中で分担するケースを表現できなくなる
- Projectの `Parent issue` / `Sub-issues progress` はGitHubが親子関係から導出する列で、
  手で設定しない。API(`gh project item-list` / GraphQLの `fieldValues`)では値が返らないため、
  紐づけの確認は `gh api repos/{owner}/{repo}/issues/{parent_number}/sub_issues` で行う

```bash
# 1. 子Issueを作る(ラベル・Project登録は通常どおり。agent:*は引き継ぎ先の階層に対応する
#    1つを選ぶ。既定はCodex優先なので `docs/model-routing.md`「既定はCodex優先」を参照。
#    phase:*は親のラベルをそのままコピーする。`phase:2-backlog`のような番号だけでは
#    表せないラベルもあるため、「フェーズ番号」ではなく親のラベル文字列そのものを使う)
gh issue create --title "..." --body "..." --label "agent:<引き継ぎ先の階層>,<親のphase:*ラベルをそのままコピー>"

# 2. 子のnumeric id(node idではない)を取って親に紐づける
SUB_ID=$(gh api repos/{owner}/{repo}/issues/{sub_number} --jq '.id')
gh api repos/{owner}/{repo}/issues/{parent_number}/sub_issues -X POST -F sub_issue_id="$SUB_ID"
```
