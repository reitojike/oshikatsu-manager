## レーン起動用の指示文テンプレート

Issueに新規着手するエージェント(レーン)をコールドスタートで起こすときに、呼び出し元
(メインセッション)が貼り付ける指示文の穴埋めテンプレート。**上の引き継ぎ計画テンプレートとは
別の用途である。**引き継ぎ計画はIssue内で判断フェーズから機械的な反復フェーズへ渡すときの
ものだが、これはIssue全体に新規着手するときのもの。

毎回書き起こしていた定型部分(必読資料と順序 / worktreeの切り方 / 止まる条件 / PR進行 /
片付けとProject更新 / 最終報告の項目)は書き写さず、下記の参照先を貼るだけにする。
埋めるのは**その回だけの固有情報**(Issue番号、担当階層、このIssue固有の作業範囲・除外事項、
競合するファイルの申し送りなど)に限る。

> stage-tracker の Issue #\<番号\> に着手します(agent:\<階層\>)。
> \<担当変更の経緯があれば1行(例: フェイルオーバー記録コメントへのリンク)\>
>
> まず `AGENTS.md` を読み、`pr-review-flow` skill を呼んでから、
> `gh issue view <番号> --comments` で本文とコメントを全部読んでください。
> (GraphQLのレート制限で失敗する場合は `gh api repos/{owner}/{repo}/issues/<番号>` と
> `gh api repos/{owner}/{repo}/issues/<番号>/comments --paginate` のREST経路に
> 切り替える。`--paginate` を付けないと、コメントが2ページ目以降にある場合に
> 後続のスコープ上書き・PO判断を読み落とす。)
>
> \<このIssue固有の前提。本文とコメントで前提が上書きされている箇所があれば読み方の
> 優先関係、最新のスコープを示すコメントへのポインタを書く\>
>
> やること: \<このIssue固有の作業範囲。対象ファイルを列挙する\>
>
> やらないこと: \<このIssue固有の除外事項\>
>
> \<並行して他Issueが同じファイルを触っている場合の申し送り。無ければ省略\>
>
> 着手時にProjectの`Status`を`In Progress`に移し、worktreeの切り方・畳み方は
> `docs/worktree-policy.md`のとおり進めてください。PRの作成からマージまでは
> `pr-review-flow` skillの手順に従ってください(Draft作成・レビュー反復・Ready化・
> マージ・マージ後の振り返りを含む)。コミット前の検証は`AGENTS.md`「作業の終わり方」の
> とおりに行ってください。
>
> レーンは待機しない(下記「レーンの待ち方」)。判断が割れている・計画に無い判断に
> 出くわしたら、自分で選ばず`docs/decision-policy.md`の手順に従ってください。

## レーンの待ち方(空転防止)

レーンはCI・レビューボットの結果を**ターンを跨いでブロッキングで**待たない。ターンの
終わり方は次の3つに限る。

1. **pushした**: 内容とSHA・残件を報告して終える
2. **何かを待っている**: 何を待っているか(CIの完了、ボットのレビューなど)を報告して終える
3. **完了した**: マージ後の振り返り・worktreeの片付け・Projectの`Status`更新まで終えたうえで、
   PR番号・マージSHA・Projectの`Status`・片付けの結果(worktree/branchを畳んだか)を報告して
   終える

呼び出し元が`gh pr checks`等で状態を直接確認し、ボット指摘の**要旨**だけを蒸留してレーンに
渡し、再開させる。完了は**プロセスの生死ではなく出力の内容**で判定する(`ps`/`jobs`が空でも
正常終了している場合がある)。

**「待たない」はターン跨ぎの空転防止だけを指し、`pr-review-flow` skillが定める検証手順
(Ready化後の最低5分待機、`Reviewed commit`のSHA一致確認、マージ直前の4面再取得)を省略
してよいという意味ではない。**これらは呼び出し元の「要旨」で代替せず、再開後にレーン自身が
skillの手順どおり実行する。呼び出し元が渡す「要旨」は、レーンを再開させるかどうかの判断
(CIが緑か、ボットの指摘が新しく付いたか)に使うものであり、マージ前の最終確認の根拠には
しない。

**バックグラウンドでポーリングを起動してターンを終える自走は採用しない。**生きた
子プロセスを残していても完了通知は抑止されないことが実測で確認されている(#138)。
