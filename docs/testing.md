# テスト方針

テストを書く前・直す前に読むこと。既存コードのリファクタ時にも読むこと。

## 構成

| ディレクトリ | environment | 依存 |
| --- | --- | --- |
| `test/unit/` | node | なし。高速。ここが主戦場 |
| `test/component/` | jsdom | Reactコンポーネント |
| `test/db/` | node | **Supabaseローカルの起動が必要**(`supabase start`) |

CIでは `test/db/` を別ジョブに分離する。`test/unit/` は依存ゼロで一瞬で終わるべき。

E2E(Playwright等)は導入していない。フェーズ1は開発者本人が使うため、
UIと手触りの確認は自分で触るほうが速い。フェーズ2で再検討する。

## 設計が先、テストは後

テストを増やす前に、**テストできる形にする**。

- ルール(フィルタ、並び順、上限、検証、整形、集計、権限判定、日付計算)は
  **それ専用のファイルのpure関数**に切り出す
- ファイル読み書き、Supabaseへのクエリ、外部通信は呼び出し側に残す
- **アプリを起動しないと到達できないルールは、テストされない**

純度を保てない境界では、**依存を引数で渡す**。現在時刻、ユーザーID、ホームディレクトリ。
import時に時計やプロセスを掴むモジュールは、環境なしにテストできない。
これは「テストしにくい」ではなく**設計の欠陥**として扱う。

### 既存コードにも適用する

これは新しい行を縛るルールではなく、**コードベースの性質として取り戻し続けるもの**。
大きなファイルを触るときは、その中に埋まっているpureなルールを引き剥がして
テストを付けるところまでを作業に含めること。

## 優先的にテストする対象

優先順位は「**どれだけ静かに失敗するか**」で決める。
例外を投げる処理は自分で報告してくれる。怖いのは**それらしく間違った値を返す**もの。

| 優先 | 対象 | なぜ静かに失敗するか |
| --- | --- | --- |
| 1 | 権限判定(`docs/permissions.md`) | 見えてはいけないものが、エラーなしで表示される |
| 2 | 削除時の分岐 | 論理削除なので、誤って消えても画面上は自然 |
| 3 | 予算集計 | 月境界、ジャンル未設定、ゼロ除算。全部それらしい数字が出る |
| 4 | カレンダーの月グリッド生成 | off-by-one。1日ずれても一見正しく見える |
| 5 | 公開/非公開の既定値 | 反転しても誰もエラーにならない |
| 6 | Web UIとMCPの挙動差 | 片方だけルールが古くなる |

## カバーするパターン

新しい関数のテストを書くときは、以下を機械的に当てること。

- **正常系**
- **エッジケース** — 変だが妥当な入力
- **コーナーケース** — エッジが複数重なる
- **境界値** — 最小/最大、off-by-one、月初/月末、うるう年
- **空** — 空文字列、空配列、空オブジェクト
- **null / undefined**
- **不正入力** — 型違い、壊れたデータ
- **エラー** — 例外が飛ぶべきところ
- **否定** — 起きてはいけないこと(権限テストではここが本体)
- **リグレッション** — 過去に出たバグ

## テストが本当に落ちるか確かめる

**新しいテストは、対象を壊したときに赤くなるかを確認する。**

- 条件を反転させる
- ガードを消す
- 修正をrevertする
- (RLSなら)ポリシーを一時的に無効化する

赤くなるのを見てから、戻す。

壊れたコードでも通るテストは、何か別のものをテストしている。
そしてこれは、**確認しない限り永遠に見えない**。

権限まわりでは特に必須。service_roleキーで書いたテストは、
RLSを全部削除しても緑のままになる(詳細は `docs/permissions.md`)。

### 実装を委譲した場合、検証は自己申告に代えない

実装を下位モデル層やCodexに委譲する運用が前提になった以上、**「壊して赤くなることを
確認した」という委譲先の自己申告を検証の代わりにしない。検証側が独立に故障注入する。**
委譲先が確認した対象と、検証側が疑うべき対象は一致するとは限らない
(PR #140: Codexが自己申告した箇所とは別の分岐が、テストされないまま残っていた)。

- **記録するのは「赤くなった」ではなく、どのテスト名が何件落ちたか。**
  復元後にベースラインの件数へ戻ることも確認する
- **diffの読みを故障注入の代わりにしない。**読みで見つかる欠陥と、実際に壊さないと
  見えない欠陥は別物である(PR #140では1回目の欠陥はdiffの読みで見つかったが、
  2回目は故障注入をするまで見えなかった)

壊して確認する作業自体は`docs/task-management.md`「Issue内でモデル階層を分担する」が言う
機械的な反復として下位モデルへ委譲できるが、それは**独立した検証者が実際に壊して確認する**
反復を渡す話であって、**実装した本人の自己申告を渡された側がそのまま信じてよい**という話
ではない。委譲先の自己申告は届け出であって、判定根拠そのものではない。

## アサーションのないテストは書けない

`sonarjs/assertions-in-tests` をerrorにしているため、CIが止める。
以前は人間が目で見つけていたもの。

## 日付まわりの注意

- 現在時刻は**引数で渡す**。`new Date()` を関数内で呼ばない
- タイムゾーンはJST前提。UTCとの変換で日付がずれる箇所をテストで固定する
- 月グリッド生成は完全なpure関数として書ける。ライブラリに委ねずdate-fnsで自前実装しているのは、
  ここをテスト可能にするため
