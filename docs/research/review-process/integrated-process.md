## 1. 単位

**1 Issue = 1判断 = 1ブランチ = 1 PR。**

PRを使う理由は1つだけで、**Rulesetで保護された `main` に入れる経路が他に無いから**である
(3草案が独立に一致)。PRは「1つの判断を包む容器」であって、レビューの単位そのものではない。
**1つのPRに2つの判断が入ると、残余(§5)の計算が破綻する** ——
どちらの判断についての残余なのかが言えなくなる。

**生成物のみの変更**(`supabase/types.ts` の再生成、整形、ロックファイル更新)は
**同じPRに混ぜず、別に流して機械ゲートのみで通す。**

**fork由来のPRは通常経路に乗せない。**理由は2つあり、どちらも単独で十分である。

1. fork PRでは `GITHUB_TOKEN` 以外のsecretがrunnerに渡らず、証拠収集に必要な権限を持てない
2. **観測範囲では、fork PR で SHA→PR の逆引きが両経路とも空だった**
   (`commits/{sha}/pulls` と `check_run.pull_requests`。2リポジトリ5 PR の実測であり、
   **「fork なら必ず空」を証明してはいない。**根拠と限界は `integration.md` §4.1・§4.3)

## 3. 契約(S0)に書くこと

**接ぎ木元: 草案C。**3草案のうちCだけが持っていた要素で、
**申告外の面に触れる変更(スコープクリープ)を機械で止める唯一の機構**である。

1. **触る面** —— ディレクトリ、テーブル、RLSポリシー、`docs/` のどのファイル
2. **変えない不変条件** —— 権限マトリクス、既定値、削除の意味論、`common/` の2経路同期
3. **変える不変条件** —— 空でなければ自動的に不可逆等級が上がる
4. **不可逆等級** —— R0 コードだけ / R1 設定・CI / R2 永続データ・マイグレーション・公開API・`docs/` の意図 /
   R3 上記のうち他者に観測済みのもの
5. **予測される残余** —— 機械が検査しないが、この変更が正しいために真である必要があること

**不可逆等級はレビューの深さを決める。**深さを行数ではなく「元に戻せなさ」に比例させる ——
**300行のUI変更より、1行の `default false` → `default true` のほうが深い。**

> **等級による分岐は、必ずゲートジョブの内側で行う。**
> job-level の `if:` や path フィルタでスキップしてはいけない。
> **skipされたjobは `"Success"` を報告し、required check であってもマージを妨げない。**
> ここを外すと、深さの分岐がそのまま「静かに通る穴」になる(3草案が独立に一次情報で確認)。

## 4. 機械が止めるもの(S2)

**レビューに何を残すかは、ここで決まる。**「入ってはいけない欠陥」を列挙し、
機械が止められるものはレビューではなくCI/型/テスト/DB権限の側に置く。
**ベンダー公式も「決定論的チェックはCIに残せ」と明記している。**

| 欠陥 | 機械が止められるか | 置き場所 |
| --- | --- | --- |
| `as` / `any` | 止められる | ESLint |
| インラインの `@ts-ignore` / `eslint-disable` | 止められる(要追加) | 抑制コメントの出現自体をCIで検出。設定ファイル側の例外だけ許す |
| 判断ロジックを `common/` 以外に置く・複製する | **部分的** | 層境界lint + **残余はレビュー** |
| Web UI と MCP の2経路が片方だけ古くなる | 止められる(要追加) | 同一入力集合を両経路に流し、結論の一致を assert する等価性テスト |
| 型の二重定義 | **部分的** | 生成型の差分検出 + **残余はレビュー** |
| 権限マトリクスの行が片方の層にしか無い | 止められる(要追加) | マトリクスを機械可読な単一データにし、RLSテストとアプリ層テストの両方をそこから駆動 |
| `test/db/` で service_role を使う | 止められる | 参照をCIで検出 |
| 既定値(参加登録の非公開)の反転 | 止められる | 既定値を固定するテスト |
| イベントの物理削除 | 止められる | DB側でDELETE権限を外し、否定側テストで固定 |
| 静かに失敗する変更に否定側テストが無い | **部分的**(要追加) | 変更行に対する故障注入。条件を反転しても緑なら赤にする。**カバレッジ率では代替できない** |
| 成果物どうしの矛盾 / 確認せず決めた判断 | **止められない** | **レビュー判断とPO確認** |
| ガバナンス文書の正本が複数箇所に増えた | **止められない** | **レビュー判断** |
| 自動化設定の権限拡大・skipの穴・永久pending・fork PRのsecret | **部分的** | 静的検査 + **残余はレビュー** |

**レビューの持ち分は、上表で「止められない」と「部分的」の残余だけである。**
移せるものをレビューに残すのは、レビューの枠を機械が言えることに食わせる分だけ損になる。

## 5. 収集と判定(S5)

### 5.1 取得の作法(3案で共通)

- **面を4つとも取る** —— `pulls/{n}/reviews` / `pulls/{n}/comments` / `issues/{n}/comments` /
  `commits/{sha}/check-runs`。**片方だけ見ると指摘を丸ごと取り落とす**
- **`per_page=100` を明示し `Link` の `rel="next"` を辿る。**既定30のまま打ち切ると静かに欠落する。
  1ページに収まると `Link` が付かないので、**`Link` の不在を異常と読まない**
- **check run は `filter=all`。**既定 `latest` では再実行前が見えない
- **スレッド解決状態は GraphQL の `PullRequestReviewThread.isResolved`。**RESTに対応フィールドが無い。
  **不在に賭けるのではなく、存在する側を使う**
- **botの同定に `login` を使わない。**`user.type == "Bot"` と既知の `user.id` の**両方一致**を要求し、
  どちらか外れたら「同定不能 = 未実行扱い」
- **reviewが増えたことを「本文が投稿された」と読まない。**`body` が空の review が作られる実例がある
- **PR番号はイベントペイロードから取る。**SHA→PR の逆引きは補助にとどめる
  (`commits/{sha}/pulls` を使う。**自前の照合表は作らない**)
- **実行回数を `run_attempt` で数えない。**あれは試行番号で初回が `1` である

### 5.2 判定の原則(3案で共通)

> **「否定の証拠が無いこと」を成功の根拠にしない。**
> 各系統について**陽性の証拠**を定義し、取れなければ「未実行」として扱う。

**「不明」は「未実行」と同じ扱いにする。**
「未実行として扱った結果どうするか」だけが論点1で変わる(§6)。

**使ってはいけない信号:**

- **CodeRabbit の commit status** —— スキップ時も `Review completed` / `success` を返す
- **Copilot の review `state`** —— 成功時も quota 拒否時も `COMMENTED` で一致する
- **ベンダーの集計API / ダッシュボード** —— 値域が表示系と食い違い、合否の根拠に使えない
- **`combined status` の `state`** —— ステータス0件のコミットは `success` ではなく `pending` になり、
  「成功」と「何も出ていない」が潰れる。`total_count` を見る
- **`bypass_actors` の `null`** —— 権限が無いと `null` が返り、「いない」と「見えない」が潰れる

**想定外の値は失敗に倒す。**check run と check suite で `conclusion` の値域が違う
(check suite だけが `stale` / `startup_failure` を持つ)ので、値域を分けて扱う。

### 5.3 指摘の処置(S6)

**指摘IDと1対1の型付き処置**を要求する。自由記述のまとめコメントにしない ——
**「読んだ」を機械が数えられる形にしないと、処置の欠落が静かに通る。**

処置は5値: **適用 / 検査に符号化 / 却下(どのルールに照らして誤りか) / Issueへ送る / 軽微として不対応。**

**ベンダーの重大度で足切りしない。**Codex の値域だけで公式(P0/P1)・他社実測(P1/P2/P3)・
アナリティクス画面(P0/P1/P2)・集計スキーマ(`p0`/`p1`/`p2`)の**4つが食い違い、確定不能**である。
**値域が確定しないものを分岐条件にすると fail-open になる。**

**受理した指摘は、可能な限り実行可能な検査に変換して残す**(テスト / lintルール / CIの検査 /
`docs/` に書かれた決定)。**符号化されない指摘は必ず再発する。**

### 5.4 残余の計算と提示(S7)

**接ぎ木元: 草案C。**

**残余 = 「この変更が正しいために真である必要があるが、S2〜S5の誰も検査していない性質」。**
**残余が空ならPO不介入でマージへ進む。空でなければ「あなたが承認するのは次のN点です」を提示する。**

これが無いと、POに渡すものが「全部」か「無」の2値になる。

## 6. 論点1で分かれる部分(**決着済み。本節は選択肢の記録である**)

> **論点1はPOが決定した(2026-08-16)。採用されたのは「必須ゲート2本」で、C案に近いが同一ではない**
> —— 2本目を特定の系統に固定しない点、自分自身を変更するPRの例外、
> 陽性証拠不足で赤になったときの出口が加わっている。
> **確定した内容は正本([`docs/review-process-design.md`](../../review-process-design.md))を見ること。**
> **本節は「何と何を比べて決めたか」の記録として残す。**

**ここだけが3案で違った。**

### 6.1 S4・S5 の扱い

| | **A案** | **C案** | **B案** |
| --- | --- | --- | --- |
| **自動で走らせる系統** | 4系統すべて | `claude-code-action`(必須)+ 3系統(任意) | **1系統のみ** |
| **required にするもの** | 我々所有の関門ジョブ1本。**その中で4系統すべての陽性証拠を要求** | `claude-code-action` の check + 自前 `review-gate` の2本 | **CI(S2)のみ。**AIレビューは required にしない |
| **系統が沈黙したとき** | **赤。**証拠が取れるまでマージできない | 必須2本は赤。**任意3系統は「残余に積む」だけで止めない** | **何もしない。**PR本文に1行記録して進む |
| **Codex の扱い** | 必須。枠切れは赤のまま待つ | 任意。「在れば読む」 | **0回。**枠を全額実装に回す |
| **Draft PR(論点2)** | 使わない —— 仕様どおりの沈黙と故障による沈黙を区別できない状態を工程に置かない | 使う —— Draft中は CodeRabbit の起動が0になる | 使わない —— `opened` と `ready_for_review` が別イベントで、2段階にすると起動が2回になる |

**論点2の根拠について:** Draft PR で SHA→PR の逆引きが壊れるという理由は**使わない。**
実測では `draft: true` かつ非fork のPRが非空を返しており、**draft は説明変数として働かなかった**
(`integration.md` §4.3)。

### 6.2 コスト(1変更あたり。通貨ごと)

**接ぎ木元: 草案B の通貨分解。**回数だけを数えると、検知を1つ足すたびに何を払ったかが言えない。

| 通貨 | A案 | C案 | B案 |
| --- | --- | --- | --- |
| **実装と共有の枠(Codex)** | 1〜3回 | 0〜2回 | **0回** |
| **レビュー専用の枠** | CodeRabbit 3 / Copilot 1〜3 | CodeRabbit 1〜2 / Copilot 0〜1 | Copilot 1〜2 のみ |
| **Actions 実行** | 3 + 再実行 | 7〜12 | 1〜2 + Copilot分 |
| **待ち時間** | 最も長い(4系統の到着待ち) | 中 | 最短 |
| **エージェントのターン** | 中 | 中〜多(契約・残余の分) | **4〜6(2巡で9〜12)** |
| **PO時間** | 0 または 1件(S8) | 0 または 1件 + 残余提示 | **0分が既定** |

**枠に収まるか。**

- **Codex —— A案は収まらない。**我々の環境の実測で、**8時間46分・23時間11分にわたり
  観測された試行がすべて拒否だった区間がある。**A案ではこの間マージできない。
  **C案・B案は必須にしないので影響を受けない**
- **CodeRabbit —— A案は週20変更を超えると Fair Usage で絞られて収まらない。**C案・B案は収まる
- **Copilot —— 3案とも事前判定できない。**残枠を返すAPIフィールドが GitHub REST に存在しない
  (全スキーマ走査で `remaining` を持つのは `rate-limit` のみ)
- **`claude-code-action` —— 3案とも収まる。**Actions minutes のみ

**Codexのレビュー枠は実装エージェントと同一プールである**(台帳、等級A2)。
**レビューを止めない側に倒すほど、実装に使える枠が増える。**

### 6.3 各案が捨てている検知

**接ぎ木元: 草案B の「削ったことで検知できなくなるもの」を、全案に対する必須の記述にした。**
**どの設計も必ず何かを捨てている。**

| | 捨てているもの |
| --- | --- |
| **A案** | ほぼ捨てていない。**代わりに可用性を捨てている** —— 枠切れの間、正しい変更もマージできない |
| **C案** | 任意3系統が全滅した変更が、残余提示のうえで通りうる。**視点の重複が保証されない** |
| **B案** | (1) **AIレビュー0回のままマージされうる。**(2) 修正pushで新しく入った欠陥。(3) 2巡目の修正で入った欠陥。(4) レビュアーが1本なので**リポジトリ固有ルールの違反検出が1系統に全依存**する。(5) 具体的には —— `common/` の2経路の片方だけが直った状態、権限判定・RLSの意味的な誤り、既定値の反転、論理削除→物理削除、型の二重定義、ドキュメント間の矛盾。**いずれもCIは緑のまま通る** |

## 7. プロセス自身の劣化を検知する(3案共通の追加)

**接ぎ木元: 草案A(canary)+ 草案C(定期監査)。**

上のすべては「PRがあるときに」しか働かない。
**設定が壊れてボットが1つも走らなくなった状態は、PRが出るまで見えない。**

- **定期の合成PR(canary)** —— 無害な差分を持つPRを定期的に開き、
  関門ジョブが陽性証拠を取れることを確認して自動でcloseする。取れなければ人に通知する
- **月次の監査** —— 系統別の受理率・却下率・空振り率を GitHub側の面から自前集計する。
  **S5が既に全面を読んでいるので、その判定結果を残せば集計は追加コストなしで付いてくる**
- **逐語文字列の照合ロジックを pure関数として切り出し、文言が変わったら赤くなるテストを付ける。**
  ベンダーの文言は実際に変わっている(CodeRabbit のレート制限見出しが
  `## Rate Limit Exceeded` → `## Rate limit exceeded`)。**文言変更を「静かに通る」から「CIが落ちる」へ変換する**

## 8. いま到達できない理想(残しておくもの)

**接ぎ木元: 草案C §9。**到達できない要素を消すと、次に何を取りに行けばよいかが失われる。

| 理想 | いまの状態 | 何が変われば到達できるか |
| --- | --- | --- |
| **レビュアーへの文脈遮断**(1周目は diff と不変条件だけを見せ、著者の意図説明を見せない) | `claude-code-action` 以外は入力チャネルを絞る設定が確認できた範囲に無い | **今日からできる代替:** 契約をSub-issueに置きPR本文を索引だけにする。**次の一手として最も安いのは** `claude-code-action` を2段構えにすること(1回目 diff のみ、2回目に契約を渡して適合を問う)。+1起動で1系統だけなら到達する |
| **必答の強制と沈黙の検出** | 構造化出力を返すのは `claude-code-action` の `--json-schema` だけ | **単一で最も効くのは、ベンダーが出力本文に1行の機械可読マーカーを入れること。**CodeRabbit は既にある。Codex と Copilot は観測範囲で0件。**これが入るだけで判定の大半が逐語文字列照合から解放される** |
| **Codex を必須ゲートに戻す** | check run も commit status も作れない(App権限が read のみ) | **Codex GitHub Action**(自前ワークフローから回す経路。設定・課金・トリガが Automatic Reviews と別立て)。**ただし併用時の重複と枠の別立ては公式に未記載なので、導入前に実測が要る** |
| **残余の完全な自動計算** | 意味判断が残る | **必答の構造化に完全従属する。**上が解ければ、残余は差集合として計算でき、追加コストなしで付いてくる |
