## 1. 要約

**この草案は、レビューを「読む営み」ではなく「著者が出した反証可能な主張を独立に検証し、
検証されなかった残余をPOに渡す営み」として設計する。**理想形の中核は9つの原理(2.1)で、
とくに次の3つが落とし込みの骨格になった。

1. **沈黙は承認ではない(fail-closed)。**「レビュアーが動かなかった」「枠を使い切った」
   「エラーで落ちた」を「指摘0件」と区別できないなら、**区別できない側を不合格に倒す。**
2. **レビューの深さは行数ではなく「元に戻せなさ」に比例させる。**
3. **未レビュー残余を機械が計算し、それだけをPOに出す。**

段階2で台帳を読んで判定した結果、**理想形18要素のうち 実現可能6 / 部分的10 / 不可2** だった。
最大の落差は**「レビュアーに必答を強制し、沈黙を検出する」**で、4系統のうち構造化出力を
持つのは `claude-code-action` の `--json-schema` → `structured_output` だけである。
したがって4節の設計では、**必須ゲートに置くのは `claude-code-action` と自前のgate checkの2つだけ**とし、
Codex Cloud / CodeRabbit / GitHub Copilot は**「在れば読む、無ければ残余に積む」**扱いにした。
これは入力5で確定した枠(quota)の制約 —— 我々の環境で**8時間46分〜23時間11分にわたり
観測されたCodexの応答がすべて拒否だった**(C1)—— から必然的に出てくる帰結でもある。

**6節の当たり直しで、台帳の1行が反証され、1行が補正された**(詳細は6節)。
**9節に「いま到達できない理想」を残した。**単一で最も効く変更は
**ベンダーが出力本文に1行の機械可読マーカーを入れること**である。

## 2. 段階1: 理想形(台帳を読む前に書いたもの)

> **この節は、`docs/research/review-tools/` の5ファイルを開く前に書いた。段階2以降の知識で
> 書き換えていない。**考えが変わった箇所は本節を直さず、4節と9節に書いた。

### 2.0 前提の言い直し

このリポジトリで「レビュー」が答えるべき問いは「このコードは読みやすいか」ではない。
**人間がdiffを読まないまま、AIが書いた変更を `main` に入れてよいと判断してよいか**である。
したがって理想形は、次の3つの事実から逆算して決まる。

1. 品質担保の第一原理は「壊れたらCIが赤くなる」。**機械が止められるものは、レビューの仕事ではない。**
   レビューの持ち分は**緑のまま間違っている変更**だけである。
2. 人間は1名(PO)で、diffを読まない。**このプロセスで最も希少な資源はPOの注意**であり、
   次にツールの起動枠、最後に実時間である。設計はPOの注意の消費量を最小化する方向に組む。
3. 変更を書くのはAIである。AIは**自分の変更について整合した説明を必ず生成できる**。
   したがって「著者の説明」はレビューの入力にはなるが、**根拠にはならない**。

### 2.1 理想形の設計原理(9つ)

**原理1: レビューは「読む」営みではなく「主張を検証する」営みである。**
著者(エージェント)は変更と同時に**反証可能な主張の集合**を出す。
「この変更は権限マトリクスを変えない」「この判断ロジックは `common/` にあり、`app/` と `mcp/` の
両方から呼ばれる」「この修正をrevertすると、これこれのテストが落ちる」。
レビューはこの主張を**独立に検証する**。主張されず、機械にも検査されていない性質は
**レビューされていない**とみなす。この「未レビュー残余」を計算できることが理想形の中核である。

**原理2: レビューの指摘は、可能な限りすべて実行可能な検査に変換されて残る。**
「今回のPRで直した」は終端状態として認めない。受理した指摘は
(a) テスト、(b) lintルール、(c) CIの検査、(d) `docs/` に書かれた決定、のいずれかになる。
どれにもならない指摘は「実行可能にできない指摘」として明示的に分類する。
理由は単純で、**符号化されない指摘は必ず再発するから**である。人間がdiffを読まない以上、
再発は次も同じレビューコストで検出するしかない。

**原理3: レビューの深さは、行数ではなく「元に戻せなさ」に比例させる。**
`docs/decision-policy.md` が「コードを消せば戻るか」で確認の要否を切っているのと同じ線を、
レビューの深さにも使う。コードだけが残る変更は、検出と revert が速ければ浅いゲートでよい。
マイグレーション、永続データの既定値、公開済みAPIの形は、revertしても戻らないので
最大のゲートを掛ける。**300行のUI変更より、1行の `default false` → `default true` のほうが深い。**

**原理4: レビュアーは著者の文脈を共有しない。**
同じセッション・同じ計画・同じモデルの続きが自分の変更をレビューすると、
著者の前提を丸ごと引き継ぐため、**前提そのものの誤りを構造的に見つけられない**。
理想は、1周目のレビュアーには「diff + リポジトリの不変条件」だけを渡し、著者の意図説明を渡さない。
2周目に初めて契約(2.2のフェーズA)を渡し、**「言ったとおりのことをしたか」**を別問として問う。
1周目は「何をしたか」、2周目は「言ったこととずれていないか」であって、混ぜない。

**原理5: レビュアーの出力は、散文ではなく再現である。**
「ここは危ういかもしれません」は検証されていない主張であって、指摘ではない。
理想形では、各指摘に**再現(壊れる入力、落ちるテスト、矛盾する2つの引用)**を要求する。
再現を伴わない指摘は「未検証の疑い」という別の等級に落とし、対応の義務を負わせない。
これはレビュアーの饒舌さと有用さを切り離すための設計である。

**原理6: テストそのものが最大のレビュー対象である。**
このリポジトリの品質は全部テストに載っている。**緑のまま間違っているテストは、
テストが無いより悪い**(無いことは気づけるが、あって効いていないことは気づけない)。
`docs/testing.md` が人手でやれと言っている「壊して赤くなるか」を、
理想形では**変更行に対する自動の故障注入(ミューテーション)**として機械化する。
著者の「赤くなるのを確認しました」という自己申告は、届け出であって根拠ではない。

**原理7: 沈黙は承認ではない(fail-closed)。**
レビュアーが動かなかった、枠を使い切った、レート制限された、内部エラーで落ちた ——
これらは「指摘0件」と**外から区別できなければならない**。区別できないなら
「レビューされていない」に倒し、マージを止める。
人間がdiffを読まない運用では、**「静かに何も起きなかった」が一番危ない**。
これは `docs/permissions.md`「権限の漏れは例外を投げない」と同じ形の失敗である。

**原理8: 承認は木(コミット)に束縛され、pushで消える。**
「古いコミットに付いた承認で、新しいコミットがマージされる」を構造的に不可能にする。
マージを許可するのは人の操作ではなく、**特定のSHAに紐づいた証跡束**である。
証跡束が欠けていればマージできない(原理7の系)。

**原理9: プロセス自身を、変更ごとではなく定期に監査する。**
誰もdiffを読まない以上、**レビュープロセスの劣化を検出する仕組みが別に要る。**
マージ後に見つかった不具合は、必ず「どのゲートが取り逃がしたか」まで辿り、
そのゲートを強くする。取り逃がしを1件も出さないことではなく、
**取り逃がしが必ずゲートの強化に変換されること**を目標にする。

### 2.2 理想形のプロセス(段階・契機・担当・判定・通過条件)

| 段階 | 発火契機 | 担当 | 何を根拠に | 通過条件 |
| --- | --- | --- | --- | --- |
| **A. 変更契約** | Issueを In Progress にした時 | 著者エージェント | Issue、`docs/`、touchする予定の面 | 契約が機械検証可能な形で揃っている。**不可逆等級R2以上ならPO確認**(コードではなく判断を確認する) |
| **B. 機械ゲート** | push ごと | CI | lint/tsc/test/生成型diff/層境界lint/RLS統合テスト | 全緑。**加えて、変更行に対する故障注入で、静かに失敗する面のミューテーションスコアが100%** |
| **C. 独立検証** | Bが緑になった時 | 独立レビュアー2系統(著者の文脈なし) | diff + リポジトリ不変条件の必答リスト | 必答リストに**全項目の明示的な判定**がある(沈黙を許さない)。P0/P1が0件 |
| **D. 契約適合** | Cの後 | 機械 | フェーズAの契約 vs 実際のdiffの面 | **申告していない面に触れていたら自動ブロック**。スコープクリープはここでだけ止まる |
| **E. 残余の提示** | Dの後 | 機械が生成、POが読む | B〜Dで誰も検査していない性質の一覧 | 残余が空ならPO不介入でマージ。空でなければ「あなたが承認するのは次の3点です」を提示 |
| **F. マージと事後** | Eの後 | 機械 | SHAに束縛された証跡束 | 証跡束が完全。マージ後は、後から出た不具合をゲートに変換 |
| **G. プロセス監査** | 定期(変更ごとではない) | Opus相当 | マージ済み変更のサンプル、指摘の受理/却下率 | ノイズを出すレビュアー・ルールを退役させる |

**契約(フェーズA)に書くこと** —— これが理想形で一番効く発明である。

1. **触る面**(ディレクトリ、テーブル、RLSポリシー、`docs/` のどのファイル)
2. **変えない不変条件**の明示(権限マトリクス、既定値、削除の意味論、`common/` の2経路同期)
3. **変える不変条件**があるならそれ(ここが空でなければ自動的に不可逆等級が上がる)
4. **不可逆等級** —— R0: コードだけ / R1: 設定・CI / R2: 永続データ・マイグレーション・
   公開API・`docs/` の意図 / R3: 上記のうち他者に観測済みのもの
5. **予測される残余** —— 「機械が検査しないが、この変更が正しいために真である必要があること」

**必答リスト(フェーズC)** —— レビュアーは各項目に「該当なし/検査済み・問題なし/問題あり」の
いずれかを**必ず**返す。返さない項目があればレビューは不成立(原理7)。

- `as` / `any` / 抑制コメントによる黙殺は無いか
- 判断ロジックが `common/` の外に置かれた、または複製されていないか
- `app/` と `mcp/` の2経路が同じ `common/` を通っているか(片側だけ直っていないか)
- 型を二重定義していないか(生成型 / `z.infer` から導出しているか)
- 権限マトリクスに触れたなら、マトリクス表・RLS・`common/`・両層のテストの**4か所が同じ変更で
  揃っているか**
- 論理削除の意味論を壊していないか(物理削除、削除後のINSERT経路)
- 既定値(参加登録の公開設定=非公開)を反転させていないか。テストで固定されているか
- `test/db/` で service_role を使っていないか
- 静かに失敗する面に**否定側**のテストがあるか
- ガバナンス文書を触ったなら、**読んだ実行者の行動が変わる差**があるか

### 2.3 レビューの単位(PRを使うかどうか)

理想形では**レビューの単位は「1つの判断」であって、ブランチでもPRでもない。**
1つの判断に対して、契約・機械ゲート・独立検証・残余提示が1組付く。
機械ゲートだけで済む付随変更(生成型の再生成、フォーマット、ロックファイル)は
**同じ単位に混ぜず、別に流して機械ゲートのみでマージする**。

理想形でPRという容れ物を使う理由は1つだけ ——
**保護された `main` に入れる経路が他に無いから**である。逆に言えば、
PRは「1つの判断を包む容器」であって、「レビューの単位そのもの」ではない。
1つのPRに2つの判断が入った時点で、残余の計算が破綻する
(どちらの判断についての残余なのかが言えなくなる)。

### 2.4 反復の終わり方

理想形では**「ボットが静かになった」を終了条件にしない。**終了条件は3つの連言。

1. 最終コミットSHAに対して、すべてのレビュアーが**明示的に完了を返している**
2. すべての指摘に**型付きの処置**が付いている(受理して修正 / 受理して検査に符号化 /
   却下+どのルールに照らして誤りか / Issueへ送る / 軽微として不対応)
3. 残余が空、またはPOに提示済み

**ラウンド上限は2。**3周目に入るということは、その変更が1つの判断に閉じていないという
信号なので、周回を増やさずに**変更を分割する**。これは3回ルール(機械的に解決しない)や
PO確認(判断が割れている)とは別の対処であり、混ぜない。

### 2.5 理想形が意図的に捨てているもの

- **人間による差分の目視。**復活させない。復活させた時点で他の全部が空回りする
- **レビュアー間の多数決。**独立レビュアーの結論が割れたら、割れたこと自体を信号として
  上位層のタイブレークに送る。2対1で押し切らない
- **「LGTM」という状態。**承認は自然言語ではなく、SHAに束縛された証跡である
- **網羅的なスタイル指摘。**機械が直せるものはレビュアーに出させない

## 3. 段階2: 理想形の各要素の実現可能性

| # | 理想形の要素 | 判定 | どのツールのどの機能か | 欠けるもの |
| --- | --- | --- | --- | --- |
| E1 | 変更契約を着手前に出す | 部分的 | 置き場所はIssue/Sub-issue/PR本文。CodeRabbit `pre_merge_checks` の built-in/custom checks が「PR説明・リンクissueとの整合」を Passed/Failed/Inconclusive で判定できる(custom checks は Pro+/Enterprise限定) | 契約の**形式**を機械が強制する手段。自由記述のまま |
| E2 | 契約とdiffの面を突き合わせ、申告外の面に触れたらブロック | **実現可能** | `GET /repos/{o}/{r}/pulls/{n}/files`(最大3000ファイル)+ 自前判定 + Actions の check run を required_status_checks に入れる | 3000ファイル超の差分。ただし本リポジトリでは非現実的な規模 |
| E3 | 機械ゲート(lint/tsc/test/生成型/層境界/RLS)全緑 | **実現可能** | GitHub Actions。`yarn lint && yarn typecheck && yarn test` と `test/db/` の別ジョブ | なし |
| E4 | 変更行への自動故障注入(ミューテーション) | 部分的 | 自前実装(CIジョブ)。レビュー製品側にこの機能を持つものは無い | 実行時間。変更行に限定して回す仕組みを自作する必要 |
| E5 | レビュアーに著者の意図説明を渡さない(文脈遮断) | **不可** | `claude-code-action` は `prompt` を自分で組むので遮断できる。他3系統は不可 | Codex は diff + `AGENTS.md`(公式A)、CodeRabbit は agentic exploration + learnings + リンクissue、Copilot は diff + メタデータ + full project context。**入力チャネルを絞る設定が確認できた範囲に無い**(6節) |
| E6 | 必答リストへの明示判定(沈黙の検出) | 部分的 | `claude-code-action`: `claude_args` の `--json-schema` → `structured_output` 出力(未取得なら `conclusion` を `failure` に倒す)。CodeRabbit: `pre_merge_checks` の custom checks が Passed/Failed/Inconclusive を返す(Pro+/Enterprise) | Codex と Copilot は観点指定が自由記述のMarkdownのみで、必答を強制する構造が無い |
| E7 | 各指摘に再現(壊れる入力・落ちるテスト)を要求 | 部分的 | E6 と同じ経路。スキーマの必須フィールドにできる | Codex/Copilot/CodeRabbit には指示できるだけで、欠落を機械判定できない |
| E8 | 指摘に型付き処置を付け、全件完了を機械判定 | 部分的 | GraphQL `PullRequestReviewThread.isResolved` + Ruleset `pull_request` の `required_review_thread_resolution`(「All conversations on code must be resolved before a pull request can be merged.」) | review body に**埋め込まれた**所見(Codex)と issue comment はスレッドにならず、解決状態を持たない |
| E9 | 受理した指摘が検査(テスト/lint/CI)に符号化されたことの機械判定 | 部分的 | CodeRabbit custom checks は「自然言語の決定的な指示」で合否を出せるので近似できる(Pro+/Enterprise) | 判定自体がAIの意味判断。決定論的な検査ではない |
| E10 | 未実行・枠切れ・エラーを「指摘0件」と区別(fail-closed) | 部分的 | CodeRabbit は HTMLマーカーで success / `skip review` / `rate limited` を区別できる。Codex は本文接頭辞で区別。Copilot は本文の逐語文字列のみ。自前gateで「肯定的完了痕跡が無ければ不合格」に倒せる | **どの面にも構造化フラグが無い。**GitHub側にも「実行されたが何も出さなかった」の判定フラグは無い。Codex は「スキップ」の痕跡自体が観測されていない |
| E11 | 承認をSHAに束縛し、pushで消す | **実現可能** | Ruleset `pull_request` の `dismiss_stale_reviews_on_push` / `require_last_push_approval`、`required_status_checks` の `strict_required_status_checks_policy` | ボット3系統は `COMMENTED` しか出さず approving にならないため、この機構が効くのは人間承認と自前checkに対してのみ |
| E12 | マージ許可をSHA単位の証跡束に束ねる | **実現可能** | 自前 gate の check run を required_status_checks に登録。Actions は check(commit statusではない)を生成する | required にした workflow が**走らない**と永久pendingになる。ゲートジョブは常に走らせる必要がある |
| E13 | 未レビュー残余の自動計算とPOへの提示 | 部分的 | 計算は自前。提示面はIssueコメント/PR本文 | 「機械が検査していない性質」の同定に意味判断が残る。E6が入るまで完全自動化できない |
| E14 | レビュー深さを不可逆等級に比例させる | **実現可能** | 変更パス(`supabase/migrations/`、`docs/permissions.md`、RLS)からの自前分類。ゲート内で分岐 | **ジョブレベルの `if:` でスキップしてはいけない**(skipped job は Success を返し、required でもマージを止めない) |
| E15 | 1PR=1判断に閉じる | 部分的 | 運用ルール。契約(E1)の「判断の個数」欄を数えれば近似できる | 機械判定は不可。CIで強制しない |
| E16 | ラウンド上限2で打ち切り、超えたら分割 | 部分的 | 「1回の実行」の痕跡は面ごとに数え方が違う。Codex は本文の `**Reviewed commit:**` SHA が最も安定、Copilot は review エントリ単位、CodeRabbit は公式に未文書化 | 横断する単一の実行IDが無い。指摘0件・レート制限・エラーの実行は review を作らない系統がある |
| E17 | 取り逃がしをゲートの強化に変換 | 部分的 | Issue + Projects で追跡 | GitHub側に escaped-defect を構造として持つ面が無い |
| E18 | プロセス自身の定期監査(レビュアーの精度測定) | 部分的 | CodeRabbit ダッシュボード/Metrics Data API(重篤度・カテゴリ別の受理率)。Codex Analytics API の `code_review_responses`(`upvoted`/`downvoted`/`replied`) | Codex Analytics API は ChatGPT Enterprise の workspace 単位で Admin key が要る。**我々のアカウントで叩けるかは未検証**。Copilot は billing usage しか無い |

## 4. プロセスの定義(いま到達できる形)

### 4.0 単位とゲートの置き方(先に結論)

- **単位はPRを使う。**理由は1つだけで、Rulesetで保護された `main` に入れる経路が他に無いため。
  ただし**1 PR = 1判断**とし、生成型の再生成・整形・ロックファイル更新は別PRで機械ゲートのみ通す。
- **必須ゲートは2つだけ。**`claude-code-action` の check と、自前の `review-gate` check。
  **Codex Cloud / CodeRabbit / Copilot を required に置かない。**理由は7節・8節。
- **`review-gate` は常に走らせる。**path filter も job-level の `if:` も使わない。
  スキップされたジョブは `"Success"` を報告し、required check であってもマージを妨げない
  (`https://docs.github.com/en/pull-requests/reference/status-checks`、2026-08-16再取得、逐語)。
  分岐はゲートの**内側**で行う。

### 4.1 段階表

| 段階 | 発火契機 | 担当 | 出力の面 | 次へ進む条件 | 終了条件 |
| --- | --- | --- | --- | --- | --- |
| **S0 契約** | Issue を In Progress へ | 著者エージェント | Sub-issue 本文の固定見出し「変更契約」 | 5項目(触る面 / 変えない不変条件 / 変える不変条件 / 不可逆等級 / 予測残余)が埋まっている。R2 なら着手前にPO確認 | 契約が確定 |
| **S1 機械ゲート** | `pull_request` の `opened` / `synchronize` / `reopened` / `ready_for_review` | Actions | check run(required) | `yarn lint` / `yarn typecheck` / `yarn test` / `yarn test:db` / 生成型diff / 層境界lint が全緑 | 全緑 |
| **S2 故障注入** | S1 が緑 | Actions(自前) | check run(R1以上でrequired) | 変更行のうち「静かに失敗する面」(権限判定、削除分岐、集計、日付、既定値)で生存ミュータント0 | 生存0 |
| **S3 独立レビュー** | Draft 作成時 / push 時 / Ready 化時 | `claude-code-action`(必須)、Codex Cloud・CodeRabbit・Copilot(任意) | review / inline comment / issue comment / check run | — | 各系統が対象SHAに対する痕跡を出す(出さない系統は残余へ) |
| **S4 収集と判定** | S1〜S3 の後、**常に実行** | 自前 `review-gate` | check run `review-gate`(required) | 下記4.2の合格条件をすべて満たす | 合格 |
| **S5 残余の提示** | S4 合格かつ残余が空でない | 自前が生成、POが読む | Issue コメント(正)+ PR本文の固定節(索引) | POの応答1回 | 応答が付く |
| **S6 マージ** | S4 合格 かつ(残余が空 または S5 完了) | 著者エージェント | — | Ruleset の required checks が全緑、未解決スレッド0 | マージ |
| **S7 事後** | マージ後に不具合が出た時 | 人+エージェント | Issue | 「どのゲートが取り逃がしたか」の特定 | ゲート強化のPRが起票される |
| **S8 監査** | 月次(変更ごとではない) | Opus層 | Issue | 系統別の受理率・却下率・空振り率 | 退役/再調整の判断 |

### 4.2 `review-gate` の合格条件(fail-closed の実体)

**判定はすべて PR の head SHA を基準に行う。**PR番号はイベントペイロードから取り、
`GET /repos/{o}/{r}/commits/{sha}/pulls` は補助にとどめる(8節)。
読む面は **4面すべて** —— `pulls/{n}/reviews` / `pulls/{n}/comments` / `issues/{n}/comments` /
`commits/{sha}/check-runs` —— に加え、スレッド解決状態は GraphQL の
`PullRequestReviewThread.isResolved` を使う(RESTには対応フィールドもエンドポイントも無い)。

合格条件は次の5つの連言。

1. **必須レビュアーの肯定的完了痕跡がある。**`claude-code-action` の check run が
   `status == "completed"` かつ `conclusion == "success"` で、`structured_output` に
   必答リスト全項目の判定が入っている。**痕跡が無い/読めない場合は合格ではなく不合格**
   (pending にしない。pending は永久pendingの罠になる)。
2. **任意レビュアーの状態を3値に分類する。**「完了(指摘あり/0件)」「未実行(枠・エラー・スキップ)」
   「不明」。**「不明」は「未実行」と同じ扱い**にする。分類は各系統の逐語文字列で行う ——
   Codex は `### 💡 Codex Review` / `Codex Review: Didn't find any major issues.` と、
   本文の `**Reviewed commit:**` の短縮SHAが head と一致すること。
   CodeRabbit は `<!-- This is an auto-generated comment: summarize by coderabbit.ai -->` の存在と
   `skip review` / `rate limited` マーカーの不在。Copilot は quota文言・行数上限文言・
   ファイル数上限文言のいずれでもないこと。
   **CodeRabbit の commit status(`Review completed` / `success`)は判定に使わない** ——
   レビューがスキップされた事例でも同じ値を返す実測がある。
3. **未処置の指摘が0件。**インライン指摘はスレッドの `isResolved`、review body 埋め込み型と
   issue comment は PR本文の「指摘台帳」節に型付き処置(受理して修正 / 受理して検査に符号化 /
   却下+根拠ルール / Issueへ送る / 軽微として不対応)が1行ずつ書かれていること。
4. **契約適合。**`pulls/{n}/files` が返すパス集合が、S0の契約の「触る面」に収まっている。
   はみ出したら不合格。R2の面に触れているのに契約の不可逆等級がR1以下なら不合格。
5. **残余が計算済み。**必答リストで「該当なし」以外を返した項目のうち、
   機械検査(S1/S2)が対応していないものを列挙してPR本文に書き出してある。

### 4.3 各系統の役割分担(なぜ必須にしないか)

| 系統 | 役割 | 必須か | 根拠 |
| --- | --- | --- | --- |
| `claude-code-action` | 必答リストの回答者。構造化出力を返す唯一の系統 | **必須** | Actions のジョブなので check として required にできる。`--json-schema` 未充足時は自ら `conclusion` を `failure` に倒す |
| Codex Cloud | 二人目の独立レビュアー。`AGENTS.md` の `## Code Review Rules` を読む | 任意 | check run も commit status も作れない(App権限が `checks:read` / `statuses:read`。2026-08-16に自分で確認)。枠が確定不能(8節) |
| CodeRabbit | 三人目。リポジトリ全体をクローンして agentic に探索する | 任意 | 出力に機械可読マーカーがあり判定は最も容易。ただしプランごとの時間あたり上限があり、必須化すると詰まる |
| GitHub Copilot | Ready化後の最終確認1回 | 任意 | 「Copilot always leaves a 'Comment' review... Its reviews do not count toward required approvals and will not block merging.」(2026-08-16再取得、逐語)。構造的にゲートになれない |

## 7. 自己コスト見積もり

**1つの変更(1 Issue = 1判断 = 1 PR、R1、ラウンド上限2)あたり。**

| 系統 | 起動回数 | 内訳 |
| --- | --- | --- |
| `claude-code-action` | **2** | 初回push後に1回、最終push後に1回 |
| 自前 `review-gate`(Actions) | **3〜5** | push ごと(Draft作成・修正push・Ready化)+ 手動再評価 |
| S1機械ゲート(Actions) | 3〜5 | 同上 |
| S2故障注入(Actions) | 1〜2 | R1以上のときのみ、S1緑の後 |
| Codex Cloud | **0〜2** | 我々の現在のトリガー設定は `PR のオープン時`。Draft作成で1、Ready化で1(bot出力は "Mark a draft as ready" を契機に挙げるが公式ページには無い) |
| CodeRabbit | **1〜2** | `drafts` 既定 `false` のため Draft中は0。Ready後、`auto_incremental_review` 既定 `true` で push ごと |
| GitHub Copilot | **0〜1** | Ready化時の自動レビュー1回のみ。`review_on_push` は使わない |

**外部レビュー系統の起動は1変更あたり合計 1〜5回、Actions の実行は 7〜12回。**

**枠に収まるか。**

- **`claude-code-action`: 収まる。**Actions minutes を消費するが、必須は2回に固定されている。
- **CodeRabbit: おそらく収まるが確認していない。**プラン別の時間あたりPRレビュー上限は
  Free 1件/時 〜 Enterprise 12件/時。**我々のプランは台帳に記録が無い(C1行が無い)。**
  fail-closed に Free 相当(1件/時)を仮定しても、1変更 1〜2回・ラウンド上限2なら収まる。
  ただし**同じ時間帯に2つのPRを走らせると詰まる。**設計上、並行PRは2本までとする。
- **Codex Cloud: 収まらない。**料金ページの `Code Reviews / 5h` 列は全プラン `Not available` で、
  さらに 2026-07-13 の5時間ウィンドウ一時撤廃の公表と両立せず、
  **確定できるのは「`/5h` の見出しを枠の根拠に使えない」ことだけ**である。
  我々の環境の実測では、`2026-08-12T02:19:55Z` から `2026-08-13T01:31:09Z` までの
  **23時間11分14秒**、クリーンなPRで観測された応答がすべて拒否だった(無観測区間8時間38分42秒を含む)。
  **1変更あたり0〜2回という見積もりは「0回」に張り付きうる。**だから必須にしない(判断2・12)。
- **GitHub Copilot: 判別できない。**quota超過の文言は `quota limit` としか言わず、
  **どの枠が尽きたかを判別できない。**Ready後1回に絞ることで消費を最小化するが、
  「収まる」とは言えない。収まらなかったときは残余に積む。

**したがって、この設計の実効的なコストは「Actions 7〜12実行 + `claude-code-action` 2回」で、
これは枠に収まる。**外部3系統は**収まらない前提で組んである**ことが、この見積もりの結論である。

## 8. 確定不能を前提にした箇所(fail-closed の置き方)

| 確定不能なもの | 何が確定していないか | fail-closed の倒し方 |
| --- | --- | --- |
| 指摘の優先度の値域 | 公式は P0/P1 のみ、我々の実測は P0=0/P1=23/P2=6/P3=0、第三者実測は P1/P2/P3、アナリティクス画面は P0/P1/P2、集計スキーマは `p0`/`p1`/`p2` のみ。**5つの情報源が一致しない** | **重大度で足切りしない。**バッジの値に関わらず全指摘に型付き処置を要求する。`P3` が集計から落ちるのか `p2` に混ざるのかも確定不能なので、集計値をプロセスの合否に使わない |
| Codexのレビュー枠 | 5時間ウィンドウか週次か、共有範囲(リポジトリ/ユーザー/組織)、残枠を読むAPI —— いずれも確定不能 | **Codexを必須ゲートに置かない。**「1日近く1件も通らない」を異常系ではなく**正常系**として扱う。枠の回復を待つ手順を設計に入れない |
| レビューモデルの固定/選択 | 「確認できた範囲に選択手段が無い」までで、「固定である」への格上げは確定不能 | **モデルに依存する期待値を置かない。**深さの制御は `AGENTS.md` の `## Code Review Rules` と、リポジトリ単位の `徹底的コード レビュー` トグルだけを前提にする |
| Copilotのquota種別 | 文言が `quota limit` のみで種類を判別できない | quota文言を検出したら**一律「未レビュー」**に倒す。種別を推定した自動対処(クレジット追加等)を行わない |
| 「実行されたが何も出さなかった」の判定 | GitHub側に判定フラグが無く、`output` の各フィールドは部分的な信号にとどまる | **肯定的完了痕跡が無ければ不合格。**「何も無い」を成功と読まない |
| Draft PR で `commits/{sha}/pulls` が空配列になる条件 | 観測例はあるが条件は公式に未文書化 | PR番号はイベントペイロードから取り、SHA→PR 逆引きは**補助にとどめる**。逆引きが空でもゲートは動く |
| Codexの「スキップ」の痕跡 | 観測範囲に痕跡が無い(観測は標本であって列挙ではない) | 「痕跡が無い」を「未実行」と同義に扱う。設定OFF・対象外・トリガー不一致を区別しようとしない |

## 9. いま到達できない理想と、何が変われば到達できるか

**この節がこの草案の一番の価値である。**理想形を消さずに残す。

### 9.1 レビュアーへの文脈遮断(E5、不可)

**理想:** 1周目のレビュアーは diff とリポジトリの不変条件だけを見る。著者の意図説明を見ない。
**現状:** `claude-code-action` だけは `prompt` を自分で組むので遮断できる。他3系統は
PR本文・コメント・リンクissue・リポジトリ全体を読む。入力チャネルを絞る設定は
確認できた範囲に無い(CodeRabbit の `path_filters` はファイルパスにしか掛からない)。

**何が変われば到達できるか。**

- **ベンダー側:** 「レビュー入力に含めるチャネル」を選べる設定が1つ入れば解決する
  (`path_filters` の入力チャネル版)。CodeRabbit は設定スキーマが公開されているので、
  キーが1つ増えたかどうかを機械的に監視できる。
- **運用側(今日からできる代替):** **契約をSub-issueに置き、PR本文を索引だけにする。**
  ボットが読む面から著者の説明を物理的に減らす。完全な遮断ではないが、
  「著者の結論をボットが先に読む」量は確実に減る。
- **自前実装:** `claude-code-action` を**2回**起動し、1回目は diff のみ、
  2回目に契約を渡して適合を問う、という2段構えにすれば、この理想は1系統だけで実現できる。
  コストは +1起動。**これは7節の見積もりの範囲内なので、次の一手として最も安い。**

### 9.2 必答の強制と沈黙の検出(E6、部分的)

**理想:** すべてのレビュアーが必答リストの全項目に明示的に答え、欠落が機械的に検出される。
**現状:** `claude-code-action`(`--json-schema`)と CodeRabbit の custom checks(Pro+)だけ。

**何が変われば到達できるか。**

- **ベンダー側:** **出力本文に1行の機械可読マーカー(HTMLコメント)を入れるだけでよい。**
  CodeRabbit は既にやっている(`<!-- This is an auto-generated comment: ... -->`)。
  Codex と Copilot は観測範囲でマーカー0件。**この1行が入るだけで、4.2の判定の大半が
  自前の逐語文字列照合から解放される。**単一で最も費用対効果の高い変更。
- **プラン:** CodeRabbit を Pro+ にすると custom checks が使え、必答リストを
  Passed/Failed/Inconclusive で返させられる。**指摘0件と未実行の区別もここで付く。**
- **別ツール:** **Codex GitHub Action**(`openai-api-key` で自前ワークフローから Codex CLI を回す経路)は
  Codex Cloud の Automatic Reviews とは設定・課金・トリガの経路が別である。
  これを使えば Codex 系の出力を**自前のジョブの中**に閉じ込められ、check run として
  required にでき、枠も別立てになる。**Codex を必須ゲートに戻す唯一の道。**
  ただし両者の併用時の重複と枠の別立ては公式に未記載なので、導入前に実測が要る。

### 9.3 fail-closed の完全化(E10、部分的)

**理想:** 「未実行」と「指摘0件」が構造的に区別できる。
**現状:** 本文の逐語文字列に依存している。文言はベンダー都合で変わる
(CodeRabbit のレート制限見出しは 2024年 `## Rate Limit Exceeded` → 2025年 `## Rate limit exceeded` と
大文字小文字が変わっている)。

**何が変われば到達できるか。**

- **ベンダー側:** Codex の GitHub App が `checks: write` を要求すれば、check run 1つで解決する
  (現在は `checks: read`。2026-08-16に自分で確認)。
- **自前実装:** 逐語文字列の照合ロジックを `.github/scripts/` の pure関数として切り出し、
  **文言が変わったら赤くなるテスト**を付ける(`docs/testing.md` の対象範囲に入る)。
  文言変更を「静かに通る」ではなく「CIが落ちる」に変換できる。これは今日からできる。

### 9.4 変更行への自動故障注入(E4、部分的)

**理想:** テストが本当に効いているかを、著者の自己申告ではなく機械が確かめる。
**現状:** 自前実装。ミューテーションを回すランナーと、変更行に限定する仕組みが要る。

**何が変われば到達できるか。**

- **自前実装:** 対象を「静かに失敗する面」(権限判定、削除分岐、予算集計、日付計算、既定値)に
  絞れば、実行時間は現実的な範囲に収まる。**全ファイルに掛けようとすると失敗する。**
- **運用:** 当面は「委譲先の自己申告を検証の代わりにしない」を、
  `claude-code-action` の必答リストに「どのテスト名が何件落ちたか」を書かせる項目として載せる。
  自己申告ではあるが、**テスト名と件数という反証可能な形**になる。

### 9.5 残余の自動計算(E13、部分的)

**理想:** 「誰も検査していない性質」を機械が列挙し、それだけをPOに出す。
**現状:** 意味判断が残る。**E6(必答の構造化)に完全に従属している。**
必答リストが構造化されれば、残余は「『該当なし』以外を返した項目のうち、
S1/S2の機械検査が対応していないもの」として**差集合で計算できる。**
つまり9.2が解ければ、この理想は追加コストなしで付いてくる。

### 9.6 プロセス自身の監査(E18、部分的)

**現状:** Codex Analytics API は ChatGPT Enterprise の workspace 単位で Admin key が必要。
**我々のアカウントで叩けるかは未検証で、「APIが存在する」から「我々が取得できる」は導けない。**
CodeRabbit の Metrics Data API は重篤度・カテゴリ別の受理率を返すが、
実行の成功/スキップ/エラー別カウントは提供されない。

**何が変われば到達できるか。**

- **プラン:** ChatGPT Enterprise + Admin key。ただし本リポジトリの規模では過剰。
- **自前実装:** GitHub側の面(reviews / comments / スレッド解決状態)から
  「出された指摘」「受理された指摘」「却下された指摘」を月次で集計する。
  **`review-gate` が既に全面を読んでいるので、その判定結果を成果物として残せば集計は無料で付いてくる。**
  これが現実解。

### 9.7 1PR=1判断の機械判定(E15、部分的)

**現状:** 機械判定は不可。差分行数は目安であってlintではない。
**何が変われば到達できるか:** 契約(S0)に「この変更に含まれる判断」を箇条書きで書かせ、
**その個数を数える。**3個を超えたら `review-gate` を警告(不合格にはしない)にする。
機械が数えているのは「著者が申告した個数」であって実際の個数ではないが、
**申告と差分の乖離は契約適合(4.2-4)で検出できる。**

## 10. 実装に踏み込んでいないことの自己点検

- `.coderabbit.yaml` の設定値を書いていない。**設定キー名**(`path_filters`、`pre_merge_checks`、
  `auto_review.drafts` 等)は「何を判定させるか」を一意に指すために挙げたが、
  **値も、ファイルの差分も書いていない。**
- workflow YAML の差分を書いていない。4.0で「job-level の `if:` と path filter を使わない」と
  書いたのは**判定をどこに置くかという設計の線**であって、YAMLの記述ではない。
- スクリプトのコードを書いていない。4.2の逐語文字列は**判定の根拠を一意に固定するため**に
  引用したもので、正規表現・パース処理・関数の形は書いていない。
- Ruleset のルール名(`dismiss_stale_reviews_on_push` 等)を挙げたのは、
  **その機構が存在することが設計の前提条件だから**であり、有効/無効の値や
  ruleset の構成は書いていない。
- **境界線として意識したこと:** 「何を、いつ、何を根拠に、どう判定し、どうなったら通るのか」までは
  書き、「その判定をどのファイルにどう書くか」は書かない。
  4.2の合格条件5項目は前者、それを実装する `.github/scripts/` の構成は後者にあたるので触れていない。
