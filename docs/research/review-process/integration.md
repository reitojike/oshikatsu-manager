## 4. オーケストレーターによる一次情報の当たり直し(統合段階で追加)

**3草案が一致した結論#3に、3本とも到達していない事実があった。**

### 4.1 `commits/{sha}/pulls` と `check_run.pull_requests` の決定変数は fork か否かである

**草案Cは「`event: pull_request` の run では長さ0」と報告し、決定変数をイベント種別としている。**
しかしCが測ったのは `workflow-run.pull_requests`(`repos/cli/cli/actions/runs` の結果)であって、
`check-run.pull_requests` ではない。**両者は別オブジェクトの同名フィールドである。**

pinned SHA `67c14c7efb01cdeeac0ecd8cee9fae8d7a80e2aa` の OpenAPI で両方の定義を確認した(2026-08-16):

- `check-run.pull_requests`: "Pull requests that are open with a `head_sha` or `head_branch` that matches **the check**. …"
- `workflow-run.pull_requests`: "Pull requests that are open with a `head_sha` or `head_branch` that matches **the workflow run**. …"

**意味論は同一で、`items` はどちらも `pull-request-minimal`。**そこで実測した(2026-08-16)。

| 対象 | `commits/{sha}/pulls` | `check_run.pull_requests` |
| --- | --- | --- |
| `cli/cli` #14136(same-repo) | 1件 | 全check run で 1 |
| `cli/cli` #14104(same-repo) | 1件 | 全check run で 1 |
| `vercel/next.js` #97421(same-repo) | 1件 | 全check run で 1 |
| `cli/cli` #14155(**fork**) | **0件** | 全check run で **0** |
| `vercel/next.js` #97420(**fork**) | **0件** | 全check run で **0** |

**2リポジトリ横断で、same-repo 3件はすべて非空、fork 2件はすべて空。**
**決定変数は fork か否かであって、イベント種別ではない。**
機序は定義文と整合する —— fork PR の head **branch** は別リポジトリに属するため `head_branch` 一致が成立しない
(head SHA 自体は base リポジトリからも解決できることを確認済みなので、「コミットが無い」ではない)。

**これは標本であって列挙ではない。**2リポジトリ5 PR の観測であり、
「fork なら必ず空」を証明していない。**しかし「イベント種別が決定変数である」というCの説明は、
このデータでは支持されない。**

### 4.2 設計への影響

1. **共通核#3(自前突き合わせを作らない)は維持される。**このリポジトリのPRは
   worktree/ブランチ運用で**すべて same-repo** であり、上記の実測では same-repo 側は両経路とも機能した。
2. **草案Cの判断11の理由づけを訂正する。**結論(PR番号はイベントペイロードから取る)は最も堅く維持されるが、
   理由は「PRイベントの run では列挙にも使えない」ではない。
3. **草案AのJ14(fork PR は常に赤)に、独立した第2の根拠が付いた。**
   Aはsecretが渡らないことを根拠にしていたが、**観測範囲では fork PR で SHA→PR の逆引き自体が両経路とも空だった**
   (§4.1 のとおり標本であり、「fork なら必ず空」は証明していない)。
   証拠収集の前提が崩れうるので、fork PR を通常経路に乗せない判断は二重に支持される。

### 4.3 マージされた訂正の帰属と、本統合の実測が食い違う

**マージされた台帳(`74d59c1`)の「check から PR を辿る」行は、次のように書いている。**

- `check_run.pull_requests` —— 「開いているPR候補の列挙には使える(open PRのみ、**fork由来は空になる**制約付き)」
- `commits/{commit_sha}/pulls` —— 「構造的な手段として機能する(実測でPR番号を返す)。
  **ただし Draft PR で空配列になる例があり、欠落の条件は公式に未文書化**」

**前者は本統合の実測と一致する。**後者の帰属が食い違う ——
**空になる条件として `Draft PR` を挙げているが、本統合の実測では draft は説明変数として働かなかった。**

2変数を分離して測り直した(2026-08-16、5 PR / 2リポジトリ)。

| PR | `draft` | `fork` | `commits/{sha}/pulls` | `check_run.pull_requests` |
| --- | --- | --- | --- | --- |
| `cli/cli` #14104 | **true** | false | **非空(1)** | 1 |
| `cli/cli` #14136 | false | false | 非空(1) | 1 |
| `vercel/next.js` #97421 | false | false | 非空(1) | 1 |
| `cli/cli` #14155 | true | **true** | 空(0) | 0 |
| `vercel/next.js` #97420 | **false** | **true** | **空(0)** | 0 |

**決定的なセルが2つある。**

- **`cli/cli` #14104 は `draft: true` かつ非fork で、非空を返した。**
  → **「Draft PR だから空になる」は反証された。**普遍主張の反証には反例1件で足りる。
- **`vercel/next.js` #97420 は `draft: false` かつ fork で、空を返した。**
  → **draft でなくても fork なら空になりうる。**

**主張の強さを非対称に置く。**

- **「draft が空の原因である」は反証された**(反例が存在するため、これは確定的に言える)
- **「fork なら空になる」は支持されたが証明されていない**(fork 2件の観測。
  標本であって列挙ではないので、「fork なら必ず空」とは言わない)

**この食い違いは #256 の設計判断に直接効く。**論点2(Draft PR を使うか)を検討する際、
マージ版の帰属をそのまま読むと**「Draft を使うと SHA→PR の逆引きが壊れる」という、
実測で支持されない理由**が Draft を避ける根拠に見えてしまう。
**本統合は、この理由を Draft の是非の根拠に使わない。**

**台帳側の訂正はこのIssueの範囲外である**(訂正作業は別Issueで走っている)。
**本書は実測を記録するにとどめ、台帳を直さない。**

## 6. 統合案

**方式:** 本文「1本をベースに選び、他から接ぎ木する」に従う。**均等にマージしていない。**

### 6.1 ベースの選定: 草案A

**理由は基準1が第一原理そのものだからではなく、Aだけが「レビューの持ち分」を導出しているからである。**
B・Cはレビューの形から設計を始めているが、Aは
**「`main` に入ってはいけない欠陥14種」→「機械が止められるか」→「残った6つだけがレビューの対象」**
という順で組んでいる。**この導出が無いと、接ぎ木した要素がどこに効くのかを言えない。**

### 6.2 接ぎ木した要素

| 出所 | 接ぎ木した要素 | なぜベースに無いと足りないか |
| --- | --- | --- |
| **C** | **変更契約(S0)と契約適合の自動ブロック** | Aは「何が入ってはいけないか」を持つが、**申告外の面に触れる変更(スコープクリープ)を止める機構が無い。**Cの契約適合は、3本のうち唯一これを機械で止める |

### 6.4 統合案が意図的に埋めていない1点

**§3の割れた軸 —— 利用できないレビュアーはマージをどこまで止めるか —— を、統合案は決めていない。**
