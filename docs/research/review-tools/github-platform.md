レビューボットが動く土台としての **GitHub プラットフォーム自身の仕様**（webhookイベント、Checks/Status、
レビューオブジェクト、required check、timeline、レート制限）を一次情報から台帳化したもの。
「どのボットが何を出すか」ではなく「GitHubがそれをどう表現するか」だけを記録する。

## 等級の凡例

| 等級 | 定義 |
| --- | --- |
| A | 公式ドキュメントを一次情報として確認した(記載の有無は状態列が示す) |

| C2 | 第三者の公開リポジトリでの実測 |

## 情報源の独立性について(較正で判明)

**`docs.github.com/en/rest/<category>/<subcategory>` のエンドポイント本文と `docs.github.com/en/webhooks/webhook-events-and-payloads` は、`github/rest-api-description` の OpenAPI から自動生成されている。**`github/docs` の `src/rest/README.md`・`src/webhooks/README.md` がパイプラインを明記しており、`content/rest/checks/runs.md` の frontmatter にも `autogenerated: rest` がある(自動生成マーカー以降が生成物で、冒頭の intro のみ人手)。

**したがって、この範囲を等級Aとして引く行と、OpenAPI を等級Bとして引く行は、独立した2つの裏付けではない。**

独立している GitHub 側の情報源: `/en/rest/using-the-rest-api/*`(ガイド、人手)、`/en/pull-requests/**`、`/en/actions/**`、`/en/repositories/**`、`github.blog/changelog`。**GraphQL SDL は REST の OpenAPI とは別の artifact なので、B同士でも独立している。**

### 問2: 文字列照合によらない構造的な判定手段があるか

| 判定したいこと | 構造的な手段 | あるか |

| checkが成功したか | check run の `conclusion`。ただし `neutral` / `skipped` / `stale` をどちらに倒すかは値の意味論に依存する | **ある(値の解釈は別問題)** |

| どのAppが出したcheckか | check run の `app.id` / `app.slug` | **ある** |
