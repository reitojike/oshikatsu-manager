# worktreeとブランチの運用

worktreeを**切った後**の話 —— ローカル `main` の扱い、diffベースのツールを使う前の点検、
使い終わったworktree/ブランチの畳み方。
**worktreeを切る前と、`/code-review` などdiffベースのツールを使う前に読む。**

切る側のルール(いつ切るか、どこに置くか)は `AGENTS.md`「ブランチとPR」にある。ここには書き写さない。
**そのルールがなぜそうなっているか**は下記「なぜIssueごとに切るのか」に置く。

## なぜこれが必要か

issue #79(PR #80)のセルフレビューで `/code-review` を実行したところ、PR #80が一切触っていない
ファイルへの指摘が返ってきた(8並列エージェント × 2回、約50万トークン相当)。

原因は連鎖している。**どの環を切れば止まるかが、この文書の内容である。**

1. `feat/issue-65-prettier` のPRがマージされた後、そのworktreeが `git worktree remove` されずに残った
2. そのworktreeが `main` をチェックアウトしたまま握り続けた
3. ローカル `main` が `origin/main` に5コミット遅れたまま固定された
4. `main` を既定の基準にするツールが、マージ済みのPR #73・#76の差分をPR #80の変更として合算した
5. レビュー結果が汚染されていることは、CIもレビューボットも検出しない

**4と5がこの問題の性質を決めている。**汚染はコミットが1つも生まれる前、ローカルでツールを
起動した時点で起きる。CIはその瞬間を観測できないので、
`AGENTS.md`「壊れたらCIが赤くなることで品質を担保する」の外側にある。
**ここは点検の手順を短くすることでしか下げられない。**

## なぜIssueごとに切るのか

`AGENTS.md` は「Issueに着手してブランチを切るときは、同時にworktreeも切る」を**例外なし**の
ルールにしている。理由は、**メインのチェックアウトを複数のチャットが直接共有すると、
あるチャットの未コミット変更が別チャットの `git status` に混ざり込むため**である。
ブランチが分かれていてもPR以前にファイルシステムレベルで衝突する。

**例外を「並行しているときだけ」に絞れない。**並行しているかは着手前には分からず、
事後に判定しても間に合わない(混ざった後に気づくことになる)。だから全件に掛ける。

**配置先だけを固定し、branch名との一致を求めないのも意図的である。**`EnterWorktree` ツールは
branch名を `worktree-<name>` に自動生成するので、ディレクトリ名と一致させるには毎回手動リネームが
必要になる。ディレクトリ名が `.claude/worktrees/<name>` に揃っていれば棚卸しの対象は一意に決まり、
branch名の一致は何も足さない。

## ローカル `main` は参照専用にする

**`main` を作業に使わない。**コミットしない、**作業用worktreeでは**チェックアウトしない。
ローカル `main` に「`origin/main` のミラー」以上の意味を持たせない。

- **作業用worktreeでは常に作業用ブランチを使う。**`main` のチェックアウト場所は、
  メインのチェックアウト(`.claude/worktrees/` の外側にあるリポジトリ本体)1箇所に固定する。
  **「作業用worktree」と「メインのチェックアウト」を言い分ける。**gitの用語ではメインの
  チェックアウトもworktreeの1つなので、単に「worktreeでチェックアウトしない」と書くと
  `main` の置き場所まで禁止してしまい、下の更新手順と矛盾する
- **「どこにもチェックアウトしない」までは行かない。**メインのチェックアウトは人間がリポジトリを
  開く既定の場所で、detached HEADにすると通常のgit操作の読み方が変わる。1箇所に固定されていれば
  更新コマンドが一意に決まる(下記)ほうが実利が大きい

### `git fetch . origin/main:main` は使えない

issue #84の本文とコメントはこのコマンドを「定期的に実行する」手段として挙げているが、
**放置worktreeが1つも無い正常な状態でも失敗する。**

```text
fatal: refusing to fetch into branch 'refs/heads/main' checked out at '<メインのチェックアウト>'
```

gitは**いずれかのworktreeでチェックアウト中のブランチ**へのfetchを拒否する。現在のworktreeか
他のworktreeかは問わない。上の実測(exit 128)は放置worktreeが無い状態で取ったもので、
`main` を握っていたのはメインのチェックアウトである。

issue #84のとき偶然このコマンドが通ったのは、放置worktreeを削除した直後の
**`main` がどこにもチェックアウトされていない一瞬**だったからで、再現できる手順ではない。

### 更新するときはメインのチェックアウトで早送りする

```bash
# 1. リモートの現在の姿を取り込む
git fetch --prune origin

# 2. ずれ方を確認する。左(main固有のコミット数)が 0 でなければ早送りしない
git rev-list --left-right --count main...origin/main

# 3. main を握っているチェックアウトの場所を確認する(見つからない場合は下記)
git worktree list

# 4. そのチェックアウトが汚れていないことを確認する。空でなければ止めて報告する
git -C <上で出たパス> status --porcelain

# 5. origin/main に早送りし、2 と 4 をもう一度実行して「0 0」と空を確かめる
git -C <上で出たパス> merge --ff-only origin/main
```

**2を飛ばして`--ff-only`だけに頼らない。`--ff-only` は「`main` に固有のコミットがある」状態を
検出しない。**`origin/main` が `main` の祖先なら、`main` が何コミット先行していても
`Already up to date.` を返して**成功する**(exit 0。本ブランチで実測)。
`--ff-only` が弾くのは履歴が分岐してマージコミットが要る場合だけなので、
「参照専用」が守られていたかどうかは2の左側でしか確かめられない。

左が0でなかったら、そこで止めて報告する。ローカル `main` に固有のコミットがある時点で
上のルールが破られており、機械的に消してよいものかは判断が要る。

**3の結果を確かめずに4・5へ進まない。この手順は「`main` がどこかにチェックアウトされている」
ことが前提で、その前提は常に成り立つわけではない。**メインのチェックアウトがdetached HEADに
なっていたり、別のブランチに切り替わっていたりすると、`git worktree list` のどの行にも
`[main]` が出てこない。それに気づかずパスを埋めて `merge --ff-only` を打つと、
**`main` ではない別のブランチを早送りして、`main` は更新されないまま成功する。**

- `[main]` の行がある → そのパスで4・5を実行する
- **`[main]` の行が無い → この手順は使わない。`git fetch origin main:main` が直接通る。**
  fetchの拒否は「チェックアウト中であること」が条件なので、誰も握っていなければ成立する
  (上の「`git fetch . origin/main:main` は使えない」は、`main` が常に
  メインのチェックアウトに居るという通常状態を前提にした話である)

**4も飛ばさない。`--ff-only` は作業ツリーが汚れていても通る。**gitが早送りを中断するのは
未コミットの変更が更新対象のファイルと**重なる**ときだけで、重ならなければ変更を保持したまま
早送りする([git-merge](https://git-scm.com/docs/git-merge))。参照専用のはずの `main` に
未コミットの変更が乗っている状態を、`--ff-only` の成否では検出できない。

## diffベースのツールを使う前の点検

```bash
git fetch --prune origin
git rev-list --left-right --count main...origin/main
```

**出力が `0` と `0` の2つでなければ、ツールを起動しない。**
左が0でなければローカル `main` に固有のコミットがある(上のルール違反)。
右が0でなければ `main` が `origin/main` に遅れている。

そのうえで、ツールによって扱いを変える。

- **基準を指定できるなら `origin/main` を使う**(`git diff origin/main...HEAD`)。
  remote-tracking refはworktreeにチェックアウトされないので、**更新が拒否される状況が構造的に
  存在しない。**ローカル `main` の鮮度に依存しなくなるので、こちらを既定にする
- **基準を指定できないツール**(ローカル `main` を既定にする `/code-review` など)は、
  上の点検が通ってから起動する。遅れていたら先に早送りする

## 使い終わったworktree/ブランチを畳む

### いつ

**2段構えにする。**

1. **一次: PRをマージ / closeした直後。**担当したモデル自身が畳む。
   `AGENTS.md`「作業完了後は `git worktree remove` で片付ける」がこれで、新しいルールではない
2. **二次: 新しくworktreeを切る前。**一次が漏れることを前提にした網

**なぜ「セッション終了時」を強く書き直すのではなく、二次を足すのか。**issue #84で漏れたのは
一次のほうだが、同じ場所に書き足しても同じ場所で漏れる。**終了は検知できる瞬間ではない**からで、
片付けを頼みたい相手(前任者)はそのときもうセッションを閉じている。「次に来た人が畳む」なら、
トリガ(worktreeを切る作業そのもの)が必ず訪れる。

**なぜ週次などの定期でないのか。**実行主体が居ない。GitHub Actionsからローカルのworktreeは
見えないので、このリポジトリに定期実行の受け皿が無い。**機械が持てないスケジュールは運用に載らない。**

**二次を着手時に置くと、上の点検と1回で済む。**worktreeを切った直後はそのまま
`git fetch --prune origin` に続けられる。別々のタイミングに置けば、片方だけ実行される。

### 誰が

**削除してよい条件を機械の出力だけで判定できる形に落としてあるので、Haiku / Luna相当で実施できる**
(`AGENTS.md`「Haikuに任せてよいのは…」)。破壊的操作ではあるが、**白と判定できたものにしか
触らない**ので、文章を解釈する余地が残らない。

**白でないものは削除しない。**`git branch -vv` の該当行と、どの条件を満たさなかったかを報告する
だけにする。そこから先(消すか残すか)は意味判断なので、Sonnet / Terra以上が扱う。

### 削除してよい条件(白)

worktreeは次の4つを全部満たすとき。

1. 自分が今いるworktreeではない
2. **`locked` が付いていない**(下記)
3. `git -C <path> status --porcelain` が空(未コミット・未追跡の変更が無い)
4. そのworktreeが持つブランチが、下のブランチの条件を全部満たす

**worktreeを持たないブランチは、下のブランチの3条件だけで判定する。**worktreeの4条件は
「worktreeも一緒に畳む」ときにだけ課すもので、worktreeが無い候補に課すと永久に白にならない。
手順の `git worktree remove` は飛ばし、`git update-ref -d` だけを実行する。
**棚卸しで一番よく出会うのはこの形である。**一次の畳み忘れはworktreeとブランチのどちらか片方だけ
残ることが多く、このIssueの調査時点で残っていたローカルブランチ6本(`main` を除く)は、
**すべてworktreeを伴っていなかった。**なおこの6本は、下の「自動化の線引き」に出てくる
「手で消していた6本」(リモート側)とは**別の集合**である。数が同じなのは偶然で、
重なっているのは1本だけ。

ブランチは次の3つを全部満たすとき。

1. `main` ではなく、**畳もうとしているworktree以外の**worktreeにチェックアウトされていない
   (**「どのworktreeにも」ではない。**畳む対象のworktree自身は、当然そのブランチを握っている。
   ここを「どのworktreeにも」と書くと、どの候補も永久に白にならない)
2. そのブランチをheadとするPRのうち、状態が `MERGED` で**ローカルの先端と `headRefOid` が
   一致するものがちょうど1件**ある
3. **同じ先端を指すオープンなPRが無い**

**2が「マージ後にローカルでコミットを足していない」ことの証明になる。**`headRefOid` は
リモートのブランチが削除済みでも取得できる(PR #50で実測。リモートは既に無いが `9adadae` が返り、
ローカルの先端と一致した)。ブランチ名は使い回せるので **PRを名前だけで1件に決めない。**
`gh pr list --head <branch> --state all` は複数返しうる。

**3はブランチ名では確かめられない。**`gh pr list --head <branch>` は**ブランチ名で**引くので、
**別の名前のブランチが同じ先端を指しているPR**を見つけられない。3が防ぎたいのはまさにそれなので、
先端のコミットから引く。

```bash
gh api repos/{owner}/{repo}/commits/$(git rev-parse <branch>)/pulls \
  --jq '.[] | select(.state == "open") | .number'
```

**1件でも返ったら白ではない。**このAPIはコミットに紐づくPRを名前によらず返す(PR #50の先端で
実測。マージ済みPRは `state` が `closed` で返るので、オープン判定は `state == "open"` で行う)。

**`locked` のworktreeは白にしない。**`git worktree unlock` は、そのworktreeを他のセッションが
使っていないことを確認しない。`locked` は「使用中」の合図として付いていることがあり
(このPRを作業したworktree自身がそうだった)、棚卸しする側からは自分のものかどうか区別できない。
`AGENTS.md`「lock済みのworktreeは `git worktree unlock` してから削除する」は、
**自分の作業を終えて自分のworktreeを畳む一次の場面**を指す。他人の残骸を畳む二次の棚卸しでは、
`locked` は報告対象であって削除対象ではない。

### `git branch --merged` も `git branch -d` も、単独では判定に使えない

**このリポジトリはsquash mergeなので、マージ済みブランチのコミットは `main` から到達できない。**
実測: `git branch --merged origin/main` はマージ済みPRのブランチを**1本も**返さない
(#50・#71・#75・#76・#80 のブランチが全部 `--no-merged` 側に出る)。到達可能性では判定できない。

`git branch -d` の可否も、白/黒とは別の軸を見ている。実測すると、

- upstreamと同期しているブランチは **`-d` が通る**(「upstreamにはマージ済み、HEADには未マージ」
  という警告付き)。ただしこれが確かめているのは**未pushのコミットが無いこと**だけで、
  PRがマージされたかは見ていない。オープンなPRのブランチでも同じように通る
- upstreamが `[gone]` のブランチは **`-d` が「not fully merged」で拒否する。**
  だが `docs/haiku-task-boundary`(PR #50はマージ済み。白)も `pr-80`(対応PRが存在せず、
  先端が `origin/main` の祖先でもない。黒)も**同じ文言で拒否される**

**そこで削除には `-D` ではなく `git update-ref -d` を使う。**

```bash
git update-ref -d refs/heads/<branch> <白の条件2で一致を確認した headRefOid>
```

`update-ref -d` は**第2引数のOIDと現在の先端が一致するときだけ削除する。**ずれていれば
`error: cannot lock ref ...: is at <実際> but expected <期待>` で失敗し、
**ブランチは残る**(両方向とも実測)。`git branch -D` は無条件に消すので、
白と判定してから削除するまでの間に誰かがそのブランチにコミットした場合を取りこぼす。

**この違いは、削除を下位モデルに任せる設計では効く。**判定と実行が別のコマンドに分かれている以上、
「判定時点の事実」を実行時に持ち込める形にしておかないと、安全性が実行者の注意深さに依存してしまう。
`-d` が拒否したことを理由に `-D` へ切り替えない。

### 手順

```bash
# 0. リモートの実態を取り込む(削除済みのリモートブランチを [gone] にする)
git fetch --prune origin

# 1. 残っているworktreeとローカルブランチを一覧する
git worktree list
git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads

# 2. 候補ごとに白の条件を確認する
git -C <worktree-path> status --porcelain
git rev-parse <branch>
gh pr list --head <branch> --state all --json number,state,headRefOid,headRefName
# 同じ先端を指すオープンPRが無いこと(名前ではなくコミットから引く)
gh api repos/{owner}/{repo}/commits/$(git rev-parse <branch>)/pulls \
  --jq '.[] | select(.state == "open") | .number'

# 3. 白のものだけ畳む(自分が中にいるworktreeは畳めない。先に出る)
#    locked は白にしないので、ここに unlock は出てこない
#    worktreeを持たないブランチでは、次の1行は飛ばす
git worktree remove <path>
git update-ref -d refs/heads/<branch> <2で一致を確認した headRefOid>

# 4. 消えたことを確認する。remove の成否だけを信じない
git worktree list
test ! -e <path>
```

**0を飛ばさない。`git branch -r` はローカルのキャッシュであって、リモートの現在の姿ではない。**
実測: このリポジトリで `git branch -r` は11本を表示したが、`git fetch --prune` を通すとうち6本は
**リモートに既に存在しなかった**(残っていたのは5本)。pruneせずに棚卸しすると、
死んでいるブランチを生きていると読み違える。

**`git worktree remove` が `Permission denied` で失敗することがある**(OneDrive同期のロックと
見られる。issue #84のOwnerコメントに実例がある)。**このとき「失敗した = 何も起きていない」とは
限らない。**実例では `.git/worktrees/<name>` のメタデータ削除だけが失敗し、
`git worktree list` からは既に外れていた。逆に、一覧から外れても物理ディレクトリが
残ることもありうる。

**だから成否ではなく結末を確かめる**(手順の4)。`git worktree list` に残っていた場合の分岐は、
**物理ディレクトリが在るかどうかで決める。**

- `test ! -e <path>` が真(実体は消えている) → `git worktree prune` でメタデータを片付ける
- 実体が残っている → **`prune` を打たずに手動対応として報告する。**`prune` は
  「実体が無い」以外の理由(`gitdir` の欠落や不正)でもメタデータを消しうるので、
  実体が残っている状態で打つと、worktreeを迷子にしたまま管理情報だけ失う
**「片付いていない」と「エラーが出た」を同一視しない。**

## 自動化の線引き

**定期実行やフックによる自動化は入れない。**

- ローカルのworktreeとブランチはGitHub Actionsから見えない。**CIゲートにできない**
- ローカルのgitフックは、GitHub上でのPRマージでは発火しない。`.git/hooks` はコミットもできない
- 破壊的操作を無人で回す仕組みは、判定条件が正しくても事故が非可逆になる

**機械に持たせるのは1つだけ。リポジトリ設定 `deleteBranchOnMerge` を有効にする**
(2026-08-09に適用。それまでは `false` だった)。適用時点のorigin上には、マージ済みPRのブランチが
4本残っていた(#71・#75・#80・#89)。**一方で他の6本は誰かが手で消していた。**
消える・残るがマージのたびに揺れていたので、片付いているかどうかを目視でしか確かめられなかった。

**この4本と、上の `--merged` の節で挙げた5本(#50・#71・#75・#76・#80)が食い違うのは、
数えている場所が違うからで、測定時期のずれではない。**前者は**origin上のリモートブランチ**、
後者は**手元のローカルブランチ**である。#50と#76はローカルにだけ残っていた(リモートは手で
消されていた)。#89は逆にリモートにだけあり、ローカルには無い。
**ローカルとリモートは別々に腐る**ので、棚卸しでは両方を見る。

- **リモート側の棚卸しがゼロコストになる。**GitHubがマージのたびに消すので、エージェントの
  記憶にも着手時の点検にも依存しない
- ローカル側は `git fetch --prune` で `[gone]` になり、**死んだブランチに機械可読な印が付く。**
  ただし `[gone]` は候補の印であって判定ではない(マージ以外の理由でリモートが消えることもある)。
  白かどうかは上のPR条件で確かめる
- **破壊的ではない。**消えるのはリモートのブランチrefだけで、内容は `main` とPRに残り、
  PR画面から復元できる
- **代わりに `git branch -d` のガードレールは効かなくなる**(upstreamが常に `[gone]` になるため)。
  これは損失ではない。上で見たとおり `-d` が確かめていたのは未pushコミットの不在だけで、
  白の条件3(`headRefOid` との一致)がそれを包含している

## 見直しのトリガ

`deleteBranchOnMerge` を入れてもなお、着手時の点検で毎回のように放置worktreeが見つかるなら、
**検出だけを行うスクリプト**(`yarn worktree:audit` 相当)を起こす。**削除までは自動化しない。**
