# イベント参加のスケジュール・予算管理アプリ PRD (v0.7)

## 1. 背景・目的

宝塚・歌舞伎・アイドルライブなど複数ジャンルのイベント参加において、以下の課題を解決する。

- 公演情報・チケット抽選/販売スケジュールの把握が煩雑で追いきれない
- 「行く予定のもの」「検討中のもの」の管理が属人化しており漏れが生じる
- ジャンル/イベントごとの支出予定・実績が可視化されておらず、予算超過に気づきにくい

併せて、開発者本人にとっては実務で使うClaude Codeの練習、およびMCPサーバー構築の学習機会とする。

## 2. 対象ユーザー

- **フェーズ1(MVP)**: 開発者本人が中心。ただし招待機能があるため、家族・友人が利用する前提でマルチユーザー設計とする
- **フェーズ2**: 家族・友人への本格展開

## 3. 画面構成の考え方

イベント情報(客観的な公演情報)と、自分の参加予定(個人的な情報)を明確に分離する。

| 画面 | 表示対象 | 主な操作 |
| --- | --- | --- |
| **イベント一覧** | 登録されている全イベント | 参加登録、他ユーザーの招待、(オーナーのみ)編集・削除 |
| **自分のスケジュール** | 自分が参加登録しているイベントのみ | ステータス更新、参加取りやめ、カレンダー表示 |
| **予算・支出** | 自分の予算枠と支出 | 予算/実績の登録、消化率の確認 |

## 4. 主要機能

### 4.1 イベント情報管理(MVP)

- 公演/ライブの基本情報を登録・閲覧できる(日時、会場、ジャンル、情報源URL)
- **イベントは全ユーザー共有のカタログ**として扱う。イベント一覧画面には登録済みの全イベントが表示される
- 編集・削除ができるのは登録者(オーナー)のみ
- 情報源:
  - アイドル: 公式サイト、X(手動確認・入力)
  - 歌舞伎: 松竹の公演ページ
  - 宝塚: 公式チケット情報サイト
  - ※協賛企業の抽選など散在情報は、当面は自動収集せず手動登録。パターンが見えてきた時点で自動化を再検討(フェーズ2以降)

### 4.2 チケット申込管理(MVP)

- 1つのイベントに対して複数の申込経路を登録できる(公式先行、協賛企業抽選、一般発売など)
- 各申込について、受付期間・当落発表日・一般発売開始日・申込結果を記録できる
- 申込情報は**個人ごと**に持つ(同じイベントでも人によって申込ルートが異なるため)

### 4.3 予定管理(MVP)

- 参加登録したイベントに対してステータスを設定できる(検討中/申込済/当選/落選/参戦決定/見送り)
- ステータス別・日付順での一覧表示
- カレンダービュー(月表示)
  - **専用ライブラリは使わず、date-fns + 自前実装とする**(理由は8.3)
  - 月表示のみ。週表示・ドラッグ&ドロップ等は実装しない

### 4.4 予算・支出管理(MVP)

- イベントごとに**支出予算(予定額)**と**支出実績**をそれぞれ登録できる
  - 内訳は任意で持てる(チケット代、遠征費、グッズ代など)
- 期間・ジャンル単位の予算枠を設定できる(月次/年次、ジャンル別または全体)
- ジャンル別/月別/年別の集計表示(予算・実績それぞれ、および差分)
- 設定した予算に対する消化率の表示
- 支出は**個人スコープ**。他ユーザーとは共有されない

### 4.5 参加登録・招待機能(MVP)

**参加登録**

- 各ユーザーがイベント一覧から自分で参加登録する
- 参加登録時に、参加を他ユーザーに**公開するか非公開にするか**を選択できる(デフォルト: 非公開)
- 参加者間に主従関係はない。イベントの編集権限はオーナーのみが持つ
- **削除済み(論理削除)のイベントには参加登録できない**(4.6)

**招待**

- そのイベントに参加登録しているユーザーは、メールアドレス指定で他ユーザーを招待できる
  - Google SSOで既にアカウントを持つユーザーのみ指定可能(未登録ユーザーの招待はスコープ外)
  - **オーナーであっても、自分自身が参加登録していなければ招待できない。**`owner_id` は
    「情報の管理者」であってイベントの主催・招待の権限を意味しないため(`docs/data-model.md`
    2章)。招待可否はオーナーかどうかではなく、参加登録の有無だけで決まる
- **MVPでは承認フローを設けない**。招待した時点で相手のスケジュールに即時反映される
- 招待された側は、自分の判断で参加を取りやめられる
- **削除済み(論理削除)のイベントには招待できない**(4.6)

**権限まとめ**

| 項目 | ルール |
| --- | --- |
| イベント情報の編集・削除 | オーナー(登録者)のみ |
| 参加登録・取りやめ | 各ユーザーが自分の分を操作(新規の参加登録は未削除のイベントに限る) |
| 他ユーザーの招待 | 参加登録している任意のユーザーが実行可能(オーナーであっても未参加なら不可。未削除のイベントに限る) |
| ステータス・公開設定の変更 | 本人のみ |
| 支出の可視範囲 | 本人のみ |

※この表は、8.4のRLS検証テストの元データとして扱う。表を変更したらテストも同時に変更する。

### 4.6 削除時のルール(MVP)

**イベントの削除**

- 論理削除とする
- オーナー本人以外の参加者が1人でもいる場合は削除不可(他ユーザーのスケジュールから勝手に消えることを防ぐため)
- **削除済みのイベントには、新たに参加登録も招待もできない**(issue #54)。
  上のガードは「削除できるのは非オーナー参加者がゼロのときだけ」という不変条件だが、
  削除**後**に参加者を増やせるとこれが事後的に破れる。オーナーであっても例外はない
  - 塞ぐのは新規登録・招待だけで、既存の参加行のステータス変更・公開設定の変更・
    参加の取りやめは削除後もできる(削除できた時点で参加者はオーナー本人しかいない)
  - 削除済みイベントの**復活**(削除の取り消し)は現状ノーガード。仕様として認めるかも含めて
    未決定で、issue #58 で扱う
- 誤登録・重複登録の後始末は当面運用でカバー。フェーズ2で管理者による強制削除を用意する
- **MVPではこのガードに例外を設けない。**`profiles.is_admin` はカラムのみ用意し、
  これを参照する権限判定はRLSにもアプリ層にも実装しない(データモデルの後付け変更を避けるため
  カラムだけ先に定義する)。実装時期は `docs/roadmap.md`「フェーズ2バックログ」

**支出データの扱い**

支出実績が登録済みかどうかで挙動を分ける。

| ケース | 予算のみ(実績未登録) | 実績が登録済み |
| --- | --- | --- |
| ユーザーが参加を取りやめた | 該当ユーザーの支出データも削除 | 支出データは残す |
| オーナーがイベントを削除した | 参加者の支出データも削除 | 支出データは残す |

- 考え方: 予算はイベント実施前の見込み値なので消えても影響が小さいが、実績は家計の記録として意味を持つため保全する
- イベントは論理削除のため、支出から辿ってイベント名などの情報は常に参照できる

### 4.7 Claudeチャットインターフェース(MVP範囲に含める)

MCPサーバーを構築し、以下をツールとして公開する。

- イベント登録・更新・検索
- 参加登録・ステータスの変更
- チケット申込情報の登録・確認
- 支出の登録・予算消化状況の確認

**接続方式: stdio(ローカル実行)。フェーズ1はPC(Claude Desktop / Claude Code)からの利用に限定する。**

- MCPサーバーはローカルでサブプロセスとして起動する。Supabaseの接続情報は環境変数で渡す
- アクセス制御はOSのプロセス権限に委ねる。MCP独自の認証機構は実装しない
- **Web版・モバイル版のClaudeからの利用はフェーズ2以降に送る**(理由は下記)

**リモート化を見送る理由**

MCPの仕様上、インターネット経由でアクセスできるリモートMCPサーバーはOAuth 2.1 + PKCEの実装が必須であり、DCR・Protected Resource Metadata・Resource Indicators等の要件が伴う。Supabase Authをそのまま認可サーバーとして使える保証がなく、認証基盤の実装だけでMVP本体に匹敵する工数が見込まれる。フェーズ1の利用者は開発者本人であり、stdioでも学習目的と成功基準は満たせるため、リモート化はフェーズ2の独立した課題として扱う。

**ロジックの共有**

Web UIとMCPサーバーは同じドメインロジック・同じバリデーションスキーマを共有する。同じ操作に2つの経路があるため、判断ロジックを両側に複製しない(詳細は8.3)。

### 4.8 将来検討(フェーズ2以降・スコープ外)

- **リモートMCPサーバー化**(OAuth 2.1 + PKCE対応。Web/モバイルのClaudeからの利用)
- 情報源の自動収集(クローリング/監視)
- 招待の承認フロー、通知・リマインド機能
- 管理者画面(イベントの強制削除、重複イベントの名寄せ)
- 参加情報の限定公開(特定ユーザーにのみ公開)
- 支出の割り勘・精算管理
- 協賛企業抽選情報の自動集約
- E2Eテスト(Playwright等)の導入 ※理由は8.4
- PWAのオフライン対応(書き込みの同期・衝突解決) ※理由は5章

| 項目 | 方針 |
| --- | --- |

| PWAの範囲 | **manifest設置とインストール可能までとする。オフライン書き込みは実装しない。**同期の衝突解決がMVPの規模に対して過大なため。閲覧・登録ともオンライン前提 |

| 権限制御 | Supabase RLSによる行レベル制御。あわせてアプリ層でも権限チェックを実装。**RLSを最終防衛線、アプリ層を主たるテスト対象とする** |
| インターフェース | Web UI + MCPサーバー経由のClaudeチャット(フェーズ1はPCのみ) |
| 可用性 | **無料枠の7日無操作による一時停止を避けるため、GitHub Actionsから日次で軽量クエリを投げる**(8.6)。無料枠はバックアップ保持が0日である点に留意する |
| 品質保証 | 静的解析とテストで担保する(詳細は8章)。人力のコードレビューには依存しない |

## 6. 成功基準(MVP)

- 3ジャンル(宝塚/歌舞伎/アイドル)のイベントを登録・一覧できる
- 1つのイベントに複数の申込経路を登録し、締切・当落発表日を把握できる
- 参加ステータス管理により「行くつもりのもの」が一目でわかる
- 月次の予算消化率が確認できる
- 他ユーザーを招待すると、そのユーザーのスケジュールにイベントが表示される
- **PCのClaude(Desktop / Code)から、最低限の登録・確認操作ができる**
- 4.5の権限マトリクスの全項目が、RLS検証テストでカバーされている

## 7. 技術スタック(決定済み)

- フロントエンド/バックエンド: Next.js
- データベース/認証: Supabase (PostgreSQL + Supabase Auth / Google SSO)
- ホスティング: Vercel (Hobbyプラン)

- スキーマ定義/バリデーション: **Zod**
- テスト: **Vitest** (ユニット + DB統合)
- 静的解析: **ESLint** (typescript-eslint `strict` / eslint-plugin-sonarjs / eslint-plugin-security) +
  **markdownlint-cli2** (`docs/**/*.md` 等。詳細は`docs/lint-policy.md`)
- CI: **GitHub Actions** (ubuntu-latestのみ。実行環境がVercel/Linuxに一本化されているため複数OSは不要)
- コードレビュー: **別モデル(Codex)による自動レビューを全PRで実行**

## 8. 開発プロセス・品質方針

開発の大半をAIエージェントに任せる前提のため、「人間が差分を読んで品質を担保する」方式は採らない。代わりに**壊れたときに機械が止める仕組み**を先に用意する。

ただし**この方式で唯一止められないものがある。方針そのものが製品の意図と逆だった場合、機械はすべて緑になる。**この穴は、成果物間で記述が矛盾している場合やどちらとも取れる判断が必要な場合に、実装着手前のプロダクトオーナー確認をゲートとして置くことで塞ぐ(理由、止まる/進むの境界、確認の経路と書き方は `docs/decision-policy.md`)。

### 8.1 静的解析(最初からerrorで入れる)

新規開発であり既存コードの負債がないため、緩い設定から始めずに最初からerrorで導入する。

- サイズ・複雑さ: `max-lines-per-function` 60 / `complexity` 20 / `max-depth` 4 / `max-nested-callbacks` 4 / `sonarjs/cognitive-complexity` 15
- 型の逃げ道封鎖: `no-explicit-any` / `no-non-null-assertion` / `consistent-type-assertions` をerror
- 型情報を要するルールのうち、構文では捕まえられない4つをerror: `no-floating-promises` / `no-misused-promises` / `await-thenable` / `no-base-to-string`
- `sonarjs/assertions-in-tests` により、アサーションのないテストはCIで止める
- **例外はインラインの `eslint-disable` で消さず、設定ファイルに理由付きで記載する。**1エントリ1理由、理由が消えたらエントリも消す
- `@ts-ignore` / `@ts-expect-error` によるエラーの抑止は禁止。根本を直す

### 8.2 型の出どころ

同じ型を二重に定義しない。出どころを3つに整理し、手書きの型は原則置かない。

| 出どころ | 用途 |
| --- | --- |
| `supabase gen types typescript` の生成型 | DBのテーブル行そのもの |
| Zodスキーマ → `z.infer` | 外部入力(フォーム、MCPツール引数)の検証と型 |
| 手書き | 原則なし。上2つから導出する |

**Supabase生成型の運用: リポジトリにコミットし、CIで再生成して差分がないことを検証する。**

- 生成型を手で編集することを禁止する
- CIジョブが差分を検出したら失敗させる。これにより「マイグレーションを書いたが型の再生成を忘れた」状態がmainに入らない
- 生成コマンドは`package.json`のスクリプトに登録し、手順を記憶に頼らない

### 8.3 ロジックの配置

- フィルタ、並び順、検証、整形、集計、権限判定、日付計算といった**ルールはpure関数として専用ファイルに切り出す**。DB/ネットワークI/Oは呼び出し側に残す
- **Web UIとMCPサーバーの両方が判断に使うものは共通モジュールに置き、両側に複製しない。**「同期を保つこと」というコメント付きのコピーは禁止する
- 境界では依存を引数で渡す(現在時刻、ユーザーIDなど)。import時に時計やプロセスを掴まない

**バリデーションスキーマの共通化**

入力検証のZodスキーマは共通モジュールに1つだけ置き、Web UIのフォーム検証とMCPツールの入力スキーマの両方がそこから導出する。二重定義した場合、片方だけ条件が緩くなっても**緩いほうを通ったデータはエラーを出さずに保存される**ため、検知できない。

**カレンダーの実装方針**

月表示のグリッド生成(月初の曜日オフセット、前後月のはみ出し日、うるう年、週の開始曜日)は境界値の誤りが生じやすく、かつ完全なpure関数として書ける。ライブラリに委ねるとこの部分のテストが書けなくなるため、date-fnsを用いて自前で実装し、グリッド生成関数をテスト対象とする。描画コンポーネントは薄く保つ。

**優先的にpure関数化する対象**

| 対象 | 切り出す内容 |
| --- | --- |
| 権限判定(4.5) | user_id・オーナーID・参加登録有無から操作可否を判定 |
| 削除時の分岐(4.6) | 実績の有無×削除の種類から、支出データの扱いを決定 |
| 予算集計(4.4) | 期間/ジャンルの絞り込み、合算、差分、消化率 |
| 公開フィルタ(4.5) | あるユーザーから見える参加情報の絞り込み |
| ステータス遷移(4.3) | 検討中/申込済/当選/落選/参戦決定/見送りの遷移可否 |
| カレンダーグリッド(4.3) | 対象月から表示セル配列を生成 |

### 8.4 テスト方針

**フレームワーク: Vitest。**environmentを分け、pure関数とDB統合は `node`、Reactコンポーネントは `jsdom` とする。DB統合テストはSupabaseの起動を要するため、CI上では別ジョブに分離する。

**E2E(Playwright等)はMVPスコープ外とする。**フェーズ1は開発者本人が使うため、UIと手触りの確認は自分で触るほうが速い。招待フローが実際に他人に使われ始めるフェーズ2で再検討する。

**RLSの検証: Supabaseローカル(`supabase start`) + Vitest。**pgTAPは採らない(テストがSQLとTypeScriptの2言語に分かれるため)。

RLS検証の必須要件:

- **service_roleキーではなく、実際に認証したユーザーのクライアントで検証する。**service_roleはRLSをバイパスするため、それで通っても何も証明できない
- **「通ること」ではなく「弾かれること」を確認する。**正常系だけのテストは、RLSを全て無効にしても緑のままになる
- 4.5の権限マトリクスを、行=操作 × 列=ロール(オーナー/参加者/無関係のユーザー)の表としてテストに写す。空欄はテスト漏れとみなす
- アプリ層の権限判定(pure関数)とRLSで、同じマトリクスを二重に検証する

RLS検証の最小セット:

| 検証 | 期待 |
| --- | --- |
| 他ユーザーの支出を読む | 0件 |
| 非公開の参加登録を他ユーザーが読む | 0件 |
| オーナー以外がイベントを更新・削除 | 失敗 |
| 他ユーザーの参加ステータスを変更 | 失敗 |
| 他人の参加登録を勝手に取りやめる | 失敗 |
| 参加者がいるイベントをオーナーが削除 | 失敗(4.6) |
| 削除済みイベントに自分で参加登録(オーナーであっても) | 失敗(4.6) |
| 削除済みイベントに他人を招待(参加登録済みの招待者であっても) | 失敗(4.6) |

**テストケースのパターン:**正常系 / エッジケース / コーナーケース / 境界値(月境界、off-by-one) / 空 / null・undefined / 不正入力 / エラー / 否定 / リグレッション

**新しいテストは、対象を壊したときに赤くなることを確認する。**条件を反転させる、ガードを消す、赤くなるのを見て戻す。特に権限まわりでは必須とする。

**テストの優先順位は「どれだけ静かに失敗するか」で決める。**例外を投げる処理より、それらしく間違った値を返す処理を先に潰す。本アプリでは以下が該当する。

1. 権限境界(RLSとアプリ層のズレ)
2. 削除時の分岐(論理削除のため、誤って消えても気づきにくい)
3. 予算集計(月境界、ジャンル未設定、ゼロ除算)
4. カレンダーの月グリッド生成(off-by-one)
5. 公開/非公開の既定値の反転
6. Web UIとMCP経由での挙動の食い違い

### 8.5 コードレビュー

- 実装したモデルとは**別のモデル**にレビューさせる。全PRで自動発火させ、人間が起動を依頼する工程を挟まない
- まずローカルで回して指摘の質を確認し、その後CIに載せる
- ボットの指摘は機械的に全適用しない。分類し、**何を直して何を意図的に見送ったかをPRにコメントする**
  (分類の正本は`pr-review-flow` skill「指摘の扱いとマージ」)
- マージ条件: 全ボットのsign off + CIグリーン + 人間の確認

### 8.6 CIに置くジョブ

| ジョブ | 内容 | ゲート |
| --- | --- | --- |
| lint / typecheck | ESLint + markdownlint-cli2 + tsc | ゲート |
| unit test | pure関数のテスト(依存なし・高速) | ゲート |
| db test | Supabaseローカル起動 + RLS検証 | ゲート |
| supabase型検証 | 生成型を再生成し、差分がないことを確認(8.2) | ゲート |
| codeレビュー | 別モデルによる自動レビュー | 参考(判定は人間) |
| keep-alive | 日次スケジュールで軽量クエリを投げ、無料枠の一時停止を防ぐ | 対象外 |

**各workflowの先頭には「これが何を守っているか」をコメントで書く。**書けないジョブは、不要か、あるいは必要なのに実際には守れていないかのどちらかである。

keep-aliveについて: 無料枠のプロジェクトは7日間の無操作で一時停止され、復元するまでアクセスできない。閾値は変更されうるため日数を決め打ちで前提とせず、日次で実行して余裕を持たせる。Vercel CronではなくGitHub Actionsを使うのは、Hobbyプランのcron数の制約を避け、CIと同じ場所に集約するため。

### 8.7 当面導入しないもの

- 重複コード検出(jscpd)・デッドコード検出(knip): コード量が増えてから効くもの。導入する場合もCIのゲートにはせず、レポートのみとする
- 複数OSでのCI: 実行環境がVercel(Linux)に一本化されているため不要
